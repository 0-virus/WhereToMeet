### 독립 검토와 성능 계측 정정

- 추천 확장 코드의 독립 검토는 Critical/Important/Minor 없음이었다. 추가 병렬/계측 검토에서는 Important1건: 한 배치25초 처리와 다른 배치60초 대기가 겹치면 경과61초에서 대기를 뺀1초가 성능으로 기록됐다. 따라서 대기 합집합만 바로잡아도 정확한 성능값이 되지 않는다.
- 새 CLI는 대기가 있는 단계의 `serviceMs`를null로 기록한다. 요약에서도 대기가 있으면 기존 숫자/null 모두 성능 표본에서 제외하고, 모드별 `latencySamples`를 공개하며, 추천20개 성능표본이 없으면 PASS를 막는다. 새 회귀에서 기존 PASS 오판을 재현한 뒤 수정했다. 최종 전체131/131·타입 검사 통과, 독립 재검토에서 Important 해소·추가 지적 없음 및 연결된 호출자 누락 없음을 확인했다.
- 병렬 실측 러너는 실행 시작 시 이전 계측 모듈을 이미 로드했다. 원시 파일은 그대로 보존하며 Matrix `serviceMs`19.091/17.265초와 백분위는 성능 근거에서 제외한다. 별도 분석의 `correctedSummary.matrix.latencySamples=0`, p50/p95=null이 현재 판정이다. 추천은 대기가0이므로14.878/27.350초가 유효하다. 순차 원문도 보존하되 새 보수적 요약에서는 대기 단계를 제외한다. 전체 정확도는 각 실행의 `within180RateAmongAllMeasuredRoutable`를 사용하며 순차 오류를 분모에서 숨기지 않는다.
- 이번 코드·검증·문서 변경만 커밋/현재upstream push 대상으로 선택한다. 비밀 설정·임시 러너·기존 과거 실측·카탈로그/승인/원격 설정은 변경하지 않았다. 단순 확인 때문에 별도 커밋을 만드는 작업이 아니다.
- 미검증/잔여 위험: 현재 코드의 전체20×100·별도6범위·589개 전체 성능, 실제 최적성/상한별554초 차이, 비단조성1사례, 현장 접근성·실제 이동·수단별 검토, 계정 조건·원격 운영·Android. 이번 두 관측은30초 내였으나 지연 여유가 작고 p95≤10초 증거가 아니다. UI/실기기는 이 서버 변경에서 재실행하지 않았다.
- 최종 문서/실측 독립 검토에서도 중요한 오류 없음. 두 원본의 시간·대기·사용량과 문서 일치, Matrix 성능 무효값의 분리, 순차 오류 포함 정확도0.5/성공짝1.0의 구분, 두 사례를 전체19/20으로 혼합하지 않은 점을 확인했다. 문서 상대 링크41개와 staged `git diff --check`가 통과했다.
