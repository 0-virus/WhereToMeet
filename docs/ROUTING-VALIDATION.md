# 경로 검증: 목적, 방법, 결과, 다음 작업

기준일: **2026-10-28** · 최신 제한 진단: **22:26 KST** · 전체 비교 근거: 2026-10-27 `62a1d4d`

**현재 결론은 실측 FAIL, 출시 차단 유지다.** TravelTime 인증과 일부 버스·철도·혼합 경로 응답은 확인했다. 그러나 100개 거점 비교에서 정확도와 성능이 목표에 못 미쳤고, 20개 시나리오 중 14번째에서 HTTP 422로 중단했다. 이번 422는 호출 속도가 아니라 **이동 허용 시간 450초보다 큰 도보 허용 시간 900초를 보낸 요청 오류**다. 10월 28일 등시간권·Matrix의 도보 시간을 전체 이동시간 이하로 제한했고, 실제 450초 요청 두 건이 HTTP 200으로 응답했다. 전체 비교의 정확도·성능 판정은 여전히 FAIL이다. 같은 날 후속 진단에서 새 표본의 오전 오차372초, 도형 후보 누락, 이동 상한에 따라554초 달라지는 도착 검색 출발시각을 확인했다. 4시간 Arrival Matrix의 최적값 가정도 재검토해야 한다.

이 문서는 **왜 검증했는가 → 어떻게 검증했는가 → 무엇이 확인됐고 왜 실패했는가 → 무엇을 더 해야 하는가** 순서로 읽는다. 최신 수치의 원본은 [재실행 JSON](validation/traveltime-rerun-2026-10-27.json), 과거 작업 이력은 [당일 worklog](worklog/2026-10-27.md)에 있다. 10월 28일의 소량 확인은 [도보 제한 검증 JSON](validation/traveltime-walking-2026-10-28.json)과 [당일 worklog](worklog/2026-10-28.md)에 별도로 기록했다.

## 1. 목적과 합격 기준

앱은 수도권의 2–4명이 정한 약속 시각까지 도착할 수 있는 만남 거점을 추천한다. 응답이 빠른 것뿐 아니라, 모든 참가자가 도착할 수 있고 전체 후보 중 좋은 선택을 추천하는지 확인해야 한다. 기준은 [승인된 구현 계획](IMPLEMENTATION.md)이다.

| 확인할 것 | 완료 기준 | 최신 판정 |
| --- | --- | --- |

**FAIL**은 실제 기준 미달을 관측했다는 뜻이고, **미완료/차단**은 판단에 필요한 증거가 부족하다는 뜻이다. HTTP 200이나 로컬 테스트 통과만으로 추천 품질·출시 준비가 통과되는 것은 아니다.

## 2. 검증 대상과 방법

### 어떤 입력을 사용했는가

[공개 시나리오](../tests/fixtures/routing-scenarios.ts)는 서울·수원·인천·성남, 참가자 2–4명, 평일·주말·심야·이른 시간·중복 출발지를 포함한 20개다. 약속은 Asia/Seoul 기준 현재보다 4시간 이상 뒤이면서 7일 이내인 다음 적합한 날짜로 생성한다. 재실행마다 미래 날짜를 생성하고 보고서에 생성 기준과 약속 시각을 남긴다.

- 소량 검증: 공개 사당 목적지 하나로 연결·시간·교통수단·파서 호환성 확인.
- 비교 검증: [100개 표본 카탈로그](../data/hubs.sample.json)의 모든 목적지 평가. 지역·종류·ID 순으로 결정적으로 선택하며 참가자 출발지와 독립적이다.
- 후속 규모 검증 대상: [현재 589개 미리보기](../data/hubs.preview.json). 두 카탈로그는 현장 검수 완료 데이터가 아니며, 출시용 [카탈로그](../data/hubs.json)는 아직 비어 있다.

2026-10-28 [거점 검수](HUB-REVIEW.md)에서 표본의 봉명역이 서비스 지역 밖인 충남 천안으로 확인됐다. 기존 100개 입력은 Git 커밋 `44a9330`에, 과거 실측 JSON은 기존 파일에 보존했다. 현재는 지역 밖 후보를 제외한 589개와 새 100개 표본을 생성하며, 새 버전의 정확도·성능을 다시 검증해야 한다. 이 표본을 검수된 출시 카탈로그로 취급하지 않는다.

### 시나리오 하나를 어떻게 검사하는가

1. **추천 계산:** 참가자별 정방향 등시간권으로 공통 후보를 좁히고 도착 경로를 확인해 최대 네 곳을 추천한다. 등시간권은 특정 시각에 출발해 주어진 시간 안에 갈 수 있는 영역이다.
2. **전체 후보 계산:** 같은 출발지·약속 시각으로 100개 거점의 Arrival Matrix를 계산하고 유효한 모든 거점을 정렬한다. 이것이 공급자 응답 기준 비교선이며 실제 이동의 정답을 대신하지는 않는다.
3. **품질·안전 비교:** 추천 1위와 Matrix 1위의 최대 부담 차이를 비교한다. 부담은 `약속 시각 − 출발 시각`으로 실제 이동과 조기 도착 대기를 포함한다. 참가자 누락, 과거 출발, 늦은 도착, 중복 거점, 시간 산술·합계 불일치도 검사한다.
4. **도달 범위 검사:** 약속 시각에서 각각 15·30·45·60·120·240분을 뺀 시점에 출발하는 도달 집합을 비교한다. 시간을 늘렸는데 갈 수 있던 거점이 사라지면 비단조성으로 기록한다. 추천 내부 탐색에도 같은 종류의 안전장치가 있다.

추천 단계에서 예외가 나면 해당 시나리오의 후속 검사는 실행하지 않는다. 추천·Matrix 이후 도달 범위 검사에서 실패하면 **비교 결과는 남지만 전체 단계 완료로 세지 않는다.** 따라서 “14개 시도 / 9개 비교 / 6개 전 단계 완료”는 서로 다른 수치다.

정확도 분모는 비교된 사례 중 Matrix가 유효 경로를 찾은 사례다. Matrix에는 경로가 있는데 추천이 비어 있으면 실패에 포함한다. 양쪽 모두 빈 결과는 별도로 세며 정확도를 올리지 않는다. 근거: [검증 CLI](../scripts/validate-routing.ts), [검증 어댑터](../server/validation-adapter.ts), [추천 엔진](../server/recommend.ts).

### 호출·시간·개인정보는 어떻게 통제했는가

Node 24.21.0과 기존 공급자 구현으로 실제 호출했다. 사용자가 **Basic 120 hits/분 가정**을 승인했다. HTTP 요청 개수가 아니라 요청 안의 검색 개수를 세고, 직전 60초 합계가 120을 넘으면 기다렸다. 계정의 확정 한도나 다른 프로세스의 사용량까지 확인한 것은 아니다.

- 종료 조건: **검증 완료 또는 공급자 HTTP 호출 거부**. 최신 CLI는 첫 비정상 HTTP 응답 이후 네트워크 재시도를 막고 종료한다. 비단조성·응답 크기 같은 로컬 검사 실패는 기록한 뒤 다음 시나리오로 진행한다.
- 서비스 시간: 경과 시간에서 **로컬 할당량 대기만 제외**한다. 본문 수신·파싱·정렬은 포함한다. p50/p95는 완료된 단계 표본으로 계산하고 실패 시간을 성공 표본으로 넣지 않는다. 전체 사용량에는 실패 단계도 포함한다.
- 시간 제한: CLI는 할당량 대기를 위해 단계별 24시간 검증 제한, HTTP 호출별 30초 제한을 사용한다. **앱의 검색 전체 30초 제한과 다르므로** 원격 운영 통과 증거가 아니다.
- 응답 제한: 정상 응답의 8 MiB 보호 한도를 유지한다. 오류 본문은 최대 64 KiB까지 읽고 공급자 코드와 민감정보를 가린 설명만 보관한다. 원시 응답·키·출발지 좌표·레이블은 보고서에 넣지 않는다.
- 진단 기록: `diagnostics.requests`에 시각·시나리오·엔드포인트·검색 수·직전 60초 hits·HTTP 상태·시간/교통 설정을 남긴다. `providerErrors`는 실패 요청 인덱스, 공급자 코드, 가린 설명·추가 정보 및 본문 판독 상태를 담는다.

운영 공급자의 재시도 정책은 변경하지 않았다. 거부 후 `Retry-After`를 기다리지 않고 중단하는 것은 진단 CLI의 정책이다. `configuredHitsPerMinute`는 실행 설정이며 계정 한도 확정이 아니다. 성공 응답의 `networkMs`는 헤더까지의 대기이고 오류 진단 때는 본문 읽기도 포함하므로 성능 판단에는 `serviceMs`를 사용한다.

### 확정한 원인: 422 요청 제약 위반

⑤의 `same-origin-two` 탐색 순서는 다음과 같다. 중복 출발지는 검색 하나로 합쳐져 각 요청은 1 hit다.

| 이동 허용 시간 `travel_time` | 도보 허용 시간 `walking_time` | HTTP | 직전 60초 hits |
| ---: | ---: | ---: | ---: |
| 1,800초 | 900초 | 200 | 93 |
| 900초 | 900초 | 200 | 94 |
| 450초 | 900초 | 422 | 95 |

공급자 오류 코드 **2**, 설명 `Invalid request json`이며 추가 정보는 `obj.departure_searches[0].transportation.walking_time`을 지목했다. 도보 허용 시간이 전체 이동 허용 시간 이하여야 한다는 메시지다. 당시 [공급자 구현](../server/travel-time.ts)은 도보 시간을 900초로 고정하여 탐색 시간을 줄이면 제약을 위반했다. 10월 28일 수정 및 실제450초200 응답으로 이 요청 생성 결함의 해소를 확인했다.

**정정:** ④의 “같은 요청 재시도 성공”은 1,800초 첫 단계만 확인한 설명이었다. 실제 실패한 450초 요청과 같지 않아 원인 해결의 증거가 아니다. ③의 오류 본문은 없어 첫 422의 세부 원인까지 직접 확정할 수는 없지만, ⑤에서 같은 시나리오의 실패 조건과 공급자 설명을 확보했다.

### 10월28일 제한 진단: 도형 누락과 비교선의 최적성 불일치

[새 진단 JSON](validation/traveltime-diagnostic-2026-10-28.json)은 22:19–22:26 KST의 공개 고정 시나리오5회 실행을 묶는다. 총27요청·135 hits 모두 HTTP200, 거부0건이며 전체 요청을 합친 직전60초 최대는113 hits다. 첫 두 실행의 창은 겹치며 합산16 hits였다. 실행별 자체 제한과 계정의 확정한도는 구분하며, 기존120 HPM 실험 가정을 계약 증거로 바꾸지 않는다. 제품 코드·출시 게이트는 변경하지 않았다.

**① 비단조성 한 사례를 좁혀 재현했다.** 10/31 14:00 약속의 weekend-north-south에서 사당 참가자(p2)의 명동성당·남대문세무서 및 국가인권위·안중근활동터가 1,800초 도형에는 들어갔다가1,912초에서 빠진다. 같은 두 시간의 Departure Matrix는 두 점 모두 도달 불가, 4시간 상한 Arrival Matrix는 부담1,928초를 반환했다. 따라서 관측한 작은 도형의 포함 여부는 경로 조회와 다르며, 도형 집합의 단조성을 실제 경로의 단조성과 같다고 볼 수 없다. 두 점은 해당 짧은 구간에서 다른 참가자(p1)의 도형에 없어서 공통 후보가 아니었지만 현재 검사는 추천 전체를 중단시킨다. 새 JSON에는 현재100개 표본의 단계별 ID와 합집합590개(옛 표본100 + 현재 후보589)의 원 집계가 구분돼 있다.

**② 새100개 표본에서 오전 사례 오차372초를 관측했다.** 10/29 08:30 약속의 weekday-bus-morning은 최종 도형2,137초에서 대청역만 남겨 추천했다. 추천의 최대 부담은2,485초였고, 같은100개를4시간 Arrival Matrix로 비교한 최선 잠실역·롯데월드몰은2,113초였다. 차이372초로180초 기준에 실패했다. 추천4.327초·전체 Matrix17.538초, 할당량 대기0초다. 이 한 사례를 p50/p95나 전체 정확도로 일반화하지 않는다. 이전237초는 옛 표본·다른 약속의 기록으로 보존한다.

잠실역·롯데월드몰은2,137초와2,250초 도형에서 양쪽 참가자 모두 제외됐지만, 같은 출발시각·상한의 Departure Matrix는 두 참가자가 약속 전에 도착하는 허용 수단 경로를 반환했다. 이는 해당 거점의 도형 누락 근거다. 최종 도착 경로 검사만으로는 앞에서 제외한 거점을 되찾지 못한다. 공식 [등시간권 명세](https://docs.traveltime.com/api/reference/isochrones)는 기본 render_mode가 time-filter에 최대한 근접하는 근사임을 설명하며, 모든 점의 포함 일치나 단조성을 보장한다는 근거로 사용하지 않는다.

| ---: | --- | --- | ---: |
| 14,400초 | 07:48:35 | 08:28:41 | 2,485초 |

현재 판정은 **FAIL 및 출시 차단 유지**다. 이후 정확도 수치는 특정 상한의 Arrival Matrix 응답에 대한 비교임을 명시한다. 안전장치를 삭제하거나 상한을 임의 축소해 해결로 처리하지 않는다. 다음 단계는 공개 fixture·카탈로그 버전·정확한 약속/시간 상한으로 공급자 설명과 응답 차이를 확인하고, 도형 후보 누락을 보완할 방법을 별도로 검증하는 것이다. 공급자에게 메시지를 보내지는 않았다. 이 진단은 현장 이동·전체20×100·589개 추천 규모·운영30초·Android 검증을 대신하지 않는다.

### 저장된 오전 응답의 후보 재결합 비교

[오프라인 비교 JSON](validation/candidate-replay-2026-10-28.json)은 위 실제 응답의 SHA-256·표본 버전·약속 시각을 고정하고 후보 집합만 재결합한 분석이다. API 호출0건이며 새 경로·좌표를 만들지 않았다. **대안 엔진을 실행하거나 새로 측정한 성공 결과가 아니다.**

최종 도형은2,137초지만 검증된 대청역 부담은2,485초였다. 저장된 도형 중 이 부담 이상인 최소 시간은2,700초이며, 해당 공통 후보에는 잠실역·롯데월드몰이 이미 포함돼 있다. 즉 이 사례의 최선 비교 후보는 탐색 중 한 번 관측됐지만 최종 범위를 좁히며 버려졌다. 정확히2,485초인 도형은 없어 보간하거나 같은 결과라고 가정하지 않는다.

| 후보 집합 | 후보 수 | 저장된4시간 Matrix 중 최선 부담 | 같은 비교선 전체 최선과 차이 | 추가 Matrix hits / 요청 |
| --- | ---: | ---: | ---: | ---: |
| 현재 최종2,137초 | 1 | 2,485초 | 372초 | 0 / 0 |
| 검증 부담 이상 최소 저장 범위2,700초 | 5 | 2,113초 | 0초 | 4 / 1 |
| 조회한 모든 공통 후보 합집합 | 27 | 2,113초 | 0초 | 26 / 3 |

추가 사용량은 기존 대청역 응답을 재사용하고 새 후보만 기존10개 단위 Matrix 배치로 검증하며 재시도가 없다는 계산이다. API 사용량·지연의 실측이나 계정 한도 승인이 아니다.2,700초 집합은 비교선2위 산성역을 여전히 놓친다.27개 합집합은 저장된 비교선 상위4개를 모두 포함하지만 다른 시나리오에서의 후보 수·30초 제한·p50/p95는 알 수 없다.

다음 실험은 검증 부담을 바탕으로 기존 범위의 후보를 다시 확인하는 방식을, 후보 예산·실제 응답 시간·여러 시나리오의 누락률과 함께 평가하는 것이다. 이 한 사례에 맞춘 범위나 상한을 제품에 고정하지 않는다. 특히 짧은 Arrival 상한에서 대청역 부담1,931초가 나온 별도 관측은 그대로 남아 있어, 여기서 사용한4시간 비교선의1위를 실제 최적 지점으로 승인할 수 없다. 비단조성 안전장치·추천 엔진·기존 실측JSON·출시 판정은 변경하지 않았다.

### 확인했지만 확대 해석하면 안 되는 사실

최신 실행의 경로 표본 2,310개에서 공급자 `travel_time`은 모두 약속 시각까지의 부담과 같았고, 실제 출발–도착 차이와 같은 표본은 22개였다. 타임스탬프로 실제 이동과 조기 도착 대기를 나누는 구현을 유지한다. 표본은 재측정·중복을 포함하며 독립된 실제 여행 횟수가 아니다.

현재 파서는 지원하지 않는 `train` 등을 제외한다. 버스·철도 구간 응답만으로 도시 교통수단 범위, 가장 늦은 출발의 최적성, 현장 시간표 정확도가 모두 입증되지는 않는다. 10월27일 로컬 테스트 전체100/100·경로 검증 도구20/20, 10월28일 도보 제약 수정 후 전체110/110 및 타입 검사는 통과했지만 실제 API 실패를 상쇄하지 않는다.

```powershell
node --env-file=.dev.vars scripts/validate-routing.ts --mode compare --catalog data/hubs.preview.json --catalog-size all --out artifacts/routing-full-catalog.json
```

`TRAVELTIME_HITS_PER_MINUTE` 또는 `--hits-per-minute`로 한도를 지정한다. 이번 실험은 승인된 가정 `--hits-per-minute 120`을 사용했다. 독립 CLI 실행 간에는 사용량 창이 공유되지 않으므로 이전 마지막 호출 후 최소 60초 간격을 두고 같은 키의 다른 사용량도 고려한다. 거부 발생 시 작업의 중단 조건을 따르며 다음 명령을 자동 실행하지 않는다.

`compare`는 추천과 전체 Matrix를 짝지어 비교한다. `isochrone`·`matrix`는 개별 측정용이며 단독으로 비교 품질을 승인할 수 없다. 종료 코드 0은 PASS, 1은 측정 실패, 2는 차단·불완전한 증거다. 사람의 검토가 필요한 조건을 도구가 자동 해제하지 않는다.

보고서에서는 `summary`의 판정·표본 수 → `results`의 사례별 비교·오류 → `diagnostics.providerErrors[].requestIndex`에 해당하는 `diagnostics.requests` 순서로 읽는다. `totalUsage`는 실패 단계를 포함한 소모량이다. 기존 보고서는 덮어쓰지 않고 별도 파일로 남긴다.

2026-10-28부터 결과 계약 검사는 **반환된 순서 그대로** 최대 부담→부담 합계→안정적인 거점ID 정렬을 확인한다. `compareResults`가 정확도 비교를 위해 정렬하더라도 원래 순서 위반은 `unsafeRecommendations`에 집계되어 최종 FAIL이 된다. 이 필드는 참가자·시간·합계·순서 등의 계약 위반 수이며 현장의 물리적 위험 건수가 아니다. 추천은 기존 최대4개 검사도 유지하고, 전체 Matrix는4개를 넘는 정상 정렬 결과를 허용한다. 과거 실측JSON을 소급 수정하거나 이 로컬 검사로 공급자 정확도 문제를 해결한 것으로 기록하지 않는다.

## 부록. 입력 출처와 공급자 해석의 한계

출처·좌표·확인일은 [공개 시나리오 파일](../tests/fixtures/routing-scenarios.ts)에 있다. 서울 역사마스터와 [관광공사 수원 위치](https://data.visitkorea.or.kr/linkedview/3075791), [인천 위치](https://data.visitkorea.or.kr/linkedview/947611), [수원 기관 안내](https://yeyak.syf.or.kr/www/119), [성남 좌표표](https://www.seongnam.go.kr/contents/down/10458_9.pdf)를 사용했다. 2026-10-05 확인 기록이며 성남 PDF는 검색 색인 표로 확인했고 직접 다운로드는 시간 초과했다. 공개 좌표는 검수된 만남 출입구가 아니며 중복 승강장·대표점 검토도 남아 있다.

2026-10-05에는 [방향 설명](https://help.traveltime.com/en/articles/9503877-how-do-departure-and-arrival-searches-differ)과 [경로 선택 설명](https://help.traveltime.com/en/articles/8523982-how-do-the-models-determine-which-route-to-take)을 참고해 정방향 출발 영역과 도착 경로를 구분했다. 당시 [Matrix 명세](https://docs.traveltime.com/api/reference/travel-time-distance-matrix)의 도착 시각 문구와 도움말 의미가 불일치해 공급자 확인 과제로 남겼다. 이는 과거 조사 기록이며 문서의 현재 표현을 새로 확인한 주장은 아니다.

[등시간권 명세](https://docs.traveltime.com/api/reference/isochrones)·[경로 예시](https://docs.traveltime.com/api/start/routes)는 문서상 기능의 근거다. 초기 대기·가장 늦은 출발·한국 시간표·도시 교통 범위의 정확성에는 별도 증거가 필요하다. [사용량 한도](https://docs.traveltime.com/api/overview/usage-limits)와 [오류 코드](https://docs.traveltime.com/api/reference/error-codes)는 참고 자료이며, 이번 422 원인의 직접 근거는 저장한 실제 오류 응답이다.
