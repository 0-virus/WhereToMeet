## 2. 검증 대상과 방법

### 어떤 입력을 사용했는가

[공개 시나리오](../tests/fixtures/routing-scenarios.ts)는 서울·수원·인천·성남, 참가자 2–4명, 평일·주말·심야·이른 시간·중복 출발지를 포함한 20개다. 약속은 Asia/Seoul 기준 현재보다 4시간 이상 뒤이면서 7일 이내인 다음 적합한 날짜로 생성한다. 재실행마다 미래 날짜를 생성하고 보고서에 생성 기준과 약속 시각을 남긴다.

- 소량 검증: 공개 사당 목적지 하나로 연결·시간·교통수단·파서 호환성 확인.
- 비교 검증: [100개 표본 카탈로그](../data/hubs.sample.json)의 모든 목적지 평가. 지역·종류·ID 순으로 결정적으로 선택하며 참가자 출발지와 독립적이다.
- 후속 규모 검증 대상: [현재 589개 미리보기](../data/hubs.preview.json). 두 카탈로그는 현장 검수 완료 데이터가 아니며, 출시용 [카탈로그](../data/hubs.json)는 아직 비어 있다.

2026-10-28 [거점 검수](HUB-REVIEW.md)에서 표본의 봉명역이 서비스 지역 밖인 충남 천안으로 확인됐다. 기존 100개 입력은 Git 커밋 `44a9330`에, 과거 실측 JSON은 기존 파일에 보존했다. 현재는 지역 밖 후보를 제외한589개와 새100개 표본을 사용한다. 이번20개는 새 표본 `seoul-20261005-2b17e7c9e6f7`의 측정이며, 이전 입력과 수치를 직접 개선율로 비교하지 않는다. 이 표본을 검수된 출시 카탈로그로 취급하지 않는다.

### 시나리오 하나를 어떻게 검사하는가 — 기존 CLI 방식

1. **추천 계산:** 참가자별 정방향 등시간권으로 공통 후보를 좁히고 도착 경로를 확인해 최대 네 곳을 추천한다. 등시간권은 특정 시각에 출발해 주어진 시간 안에 갈 수 있는 영역이다.
2. **전체 후보 계산:** 같은 출발지·약속 시각으로 100개 거점의 Arrival Matrix를 계산하고 유효한 모든 거점을 정렬한다. 이것이 공급자 응답 기준 비교선이며 실제 이동의 정답을 대신하지는 않는다.
3. **품질·안전 비교:** 추천 1위와 Matrix 1위의 최대 부담 차이를 비교한다. 부담은 `약속 시각 − 출발 시각`으로 실제 이동과 조기 도착 대기를 포함한다. 참가자 누락, 과거 출발, 늦은 도착, 중복 거점, 시간 산술·합계 불일치도 검사한다.
4. **도달 범위 검사:** 약속 시각에서 각각 15·30·45·60·120·240분을 뺀 시점에 출발하는 도달 집합을 비교한다. 시간을 늘렸는데 갈 수 있던 거점이 사라지면 비단조성으로 기록한다. 추천 내부 탐색에도 같은 종류의 안전장치가 있다.

추천 단계에서 예외가 나면 해당 시나리오의 후속 검사는 실행하지 않는다. 추천·Matrix 이후 도달 범위 검사에서 실패하면 **비교 결과는 남지만 전체 단계 완료로 세지 않는다.** 따라서 “14개 시도 / 9개 비교 / 6개 전 단계 완료”는 서로 다른 수치다.

정확도 분모는 비교된 사례 중 Matrix가 유효 경로를 찾은 사례다. Matrix에는 경로가 있는데 추천이 비어 있으면 실패에 포함한다. 양쪽 모두 빈 결과는 별도로 세며 정확도를 올리지 않는다. 근거: [검증 CLI](../scripts/validate-routing.ts), [검증 어댑터](../server/validation-adapter.ts), [추천 엔진](../server/recommend.ts).

### 호출·시간·개인정보는 어떻게 통제했는가 — 기존 CLI 방식

10월27일에는 Node24.21.0과 당시 공급자 구현으로 호출했다. 사용자가 **Basic 120 hits/분 가정**을 승인했다. HTTP 요청 개수가 아니라 요청 안의 검색 개수를 세고, 직전60초 합계가120을 넘으면 기다렸다. 계정의 확정 한도나 다른 프로세스의 사용량까지 확인한 것은 아니다. 최신20개 실행은 Node24.12.0이며 아래 별도 제한을 적용했다.

- 종료 조건: **검증 완료 또는 공급자 HTTP 호출 거부**. 최신 CLI는 첫 비정상 HTTP 응답 이후 네트워크 재시도를 막고 종료한다. 비단조성·응답 크기 같은 로컬 검사 실패는 기록한 뒤 다음 시나리오로 진행한다.
- 서비스 시간: 경과 시간에서 **로컬 할당량 대기만 제외**한다. 본문 수신·파싱·정렬은 포함한다. p50/p95는 완료된 단계 표본으로 계산하고 실패 시간을 성공 표본으로 넣지 않는다. 전체 사용량에는 실패 단계도 포함한다.
- 시간 제한: CLI는 할당량 대기를 위해 단계별 24시간 검증 제한, HTTP 호출별 30초 제한을 사용한다. **앱의 검색 전체 30초 제한과 다르므로** 원격 운영 통과 증거가 아니다.
- 응답 제한: 정상 응답의 8 MiB 보호 한도를 유지한다. 오류 본문은 최대 64 KiB까지 읽고 공급자 코드와 민감정보를 가린 설명만 보관한다. 원시 응답·키·출발지 좌표·레이블은 보고서에 넣지 않는다.
- 진단 기록: `diagnostics.requests`에 시각·시나리오·엔드포인트·검색 수·직전 60초 hits·HTTP 상태·시간/교통 설정을 남긴다. `providerErrors`는 실패 요청 인덱스, 공급자 코드, 가린 설명·추가 정보 및 본문 판독 상태를 담는다.

운영 공급자의 재시도 정책은 변경하지 않았다. 거부 후 `Retry-After`를 기다리지 않고 중단하는 것은 진단 CLI의 정책이다. `configuredHitsPerMinute`는 실행 설정이며 계정 한도 확정이 아니다. 성공 응답의 `networkMs`는 헤더까지의 대기이고 오류 진단 때는 본문 읽기도 포함하므로 성능 판단에는 `serviceMs`를 사용한다.

**10월29일 병렬화 이후의 계측 규칙:** `quotaWaitMs`는 겹치는 대기의 합집합으로 집계한다. 대기가 있는 단계는 다른 배치의 처리와 겹칠 수 있으므로 경과 시간에서 빼지 않고 `serviceMs=null`로 기록하며 성능 표본에서 제외한다. 대기0인 단계만 전체 본문 수신·파싱·정렬을 포함한 경과 시간을 사용한다. 모드별 `latencySamples`를 공개하고, 추천20개의 성능 표본이 모두 없으면 PASS로 판정하지 않는다. `networkMs`는 동시 요청별 합계여서 경과 시간보다 클 수 있다. 이미 전송된 요청은 공급자 거절 시점에 존재할 수 있으나, 대기 중인 요청은 재확인하여 새 전송을 막는다.

### 10월28–29일 재측정의 차이

추천 엔진·실제 공급자·검증 함수는 `656c211` 그대로 사용하고 임시 관측 러너로20개를 순차 실행했다. 추천에는30초, 별도100개 Matrix에는180초 제한을 적용했다. 추천 오류 뒤에도 HTTP거부가 없으면 Matrix를 측정했다. 따라서 이번에는20개 모두 Matrix를 확보했고 추천 오류1개를 정확도 분모에서 숨기지 않는다. 별도900–14,400초 도형6회 검사는 반복하지 않았으며 저장한 것은 실제 추천 탐색에서 조회한 집합이다.

| 4 | 에이전트 + 거점 검수 담당 | 후속 수정 후20×100 품질·도달 범위 재검증, 전체 카탈로그 규모 측정 | 이번20개 Matrix확보·정확도85%에서95% 이상으로 개선한 근거와 별도 도형 검사 필요. 현재589개 미리보기 추천 측정과 출시 거점 검수 구분 |
| 5 | 사용자/계정 담당 + 에이전트 | trial 만료·확정 한도·사용 권한, 공급자의 시간·수단 의미 확인 | 계정/공급자 근거 기록. 120 HPM 가정을 계약 증거로 대체하지 않음 |
| 6 | 사용자/테스터 + 에이전트 | 버스·철도·혼합 각 10건 검토, 실제 이동 10건, 원격 Workers·Android 검증 | 수단·출발/도착·기기·운영 30초 제한을 확인한 실제 관측 기록 |

⑤에서 미실행했던 `same-origin-four`, `duplicate-plus-distant`, `transfer-north`, `bus-rail-transfer`, `late-four`, `early-four`는 최신20개 실행에서100개 Matrix 비교까지 수행했다. 이전②의 사당 하나 호출을100개 비교로 바꿔 해석한 것이 아니다. 현재589개 전체 추천 규모 측정과 별도6범위 도형 재검사는 여전히 미실행이다. 다음 우선 작업은 위 빈 추천2개·비단조성1개와 성능 미달의 대응이며, 기존 상한별 Arrival 최적성 문제도 남는다.

출시 판단은 코드 수정 하나나 API 성공 한 번으로 바꾸지 않는다. 품질·성능·검수·현장·계정 증거를 갖춘 뒤 승인 절차에 따라 진행하며, 현재 `ROUTING_APPROVED`와 출시 차단 상태는 유지한다.

## 6. 재현 방법과 보고서 읽는 법

Node 24에서 저장소 루트 기준으로 실행한다. 현재 규칙은 서버 키를 `.dev.vars`에 두는 것이다. 과거 실험에서 `.env.local`을 사용한 이력은 보존한다. 실제 키는 Git에 없으므로 다른 환경에서는 별도 설정이 필요하다.

```powershell
# 로컬 검사·사전 점검: 외부 API 호출 없음
node --test tests/routing-validation.test.ts
node --env-file=.dev.vars scripts/validate-routing.ts --preflight-only --catalog data/hubs.sample.json

# 실제 호출: TRAVELTIME_APP_ID/API_KEY와 확인·승인된 HPM 설정 필요
node --env-file=.dev.vars scripts/validate-routing.ts --mode compare --catalog data/hubs.sample.json --out artifacts/routing-validation.json

# 앞 실행에 HTTP 거부가 없고 후속 실행 범위가 승인된 경우의 전체 규모 비교
node --env-file=.dev.vars scripts/validate-routing.ts --mode compare --catalog data/hubs.preview.json --catalog-size all --out artifacts/routing-full-catalog.json
```

`TRAVELTIME_HITS_PER_MINUTE` 또는 `--hits-per-minute`로 한도를 지정한다. 이번 실험은 승인된 가정 `--hits-per-minute 120`을 사용했다. 독립 CLI 실행 간에는 사용량 창이 공유되지 않으므로 이전 마지막 호출 후 최소 60초 간격을 두고 같은 키의 다른 사용량도 고려한다. 거부 발생 시 작업의 중단 조건을 따르며 다음 명령을 자동 실행하지 않는다.

`compare`는 추천과 전체 Matrix를 짝지어 비교한다. `isochrone`·`matrix`는 개별 측정용이며 단독으로 비교 품질을 승인할 수 없다. 종료 코드 0은 PASS, 1은 측정 실패, 2는 차단·불완전한 증거다. 사람의 검토가 필요한 조건을 도구가 자동 해제하지 않는다.

보고서에서는 `summary`의 판정·표본 수 → `results`의 사례별 비교·오류 → `diagnostics.providerErrors[].requestIndex`에 해당하는 `diagnostics.requests` 순서로 읽는다. `totalUsage`는 실패 단계를 포함한 소모량이다. 기존 보고서는 덮어쓰지 않고 별도 파일로 남긴다.

2026-10-28부터 결과 계약 검사는 **반환된 순서 그대로** 최대 부담→부담 합계→안정적인 거점ID 정렬을 확인한다. `compareResults`가 정확도 비교를 위해 정렬하더라도 원래 순서 위반은 `unsafeRecommendations`에 집계되어 최종 FAIL이 된다. 이 필드는 참가자·시간·합계·순서 등의 계약 위반 수이며 현장의 물리적 위험 건수가 아니다. 추천은 기존 최대4개 검사도 유지하고, 전체 Matrix는4개를 넘는 정상 정렬 결과를 허용한다. 과거 실측JSON을 소급 수정하거나 이 로컬 검사로 공급자 정확도 문제를 해결한 것으로 기록하지 않는다.

## 부록. 입력 출처와 공급자 해석의 한계

출처·좌표·확인일은 [공개 시나리오 파일](../tests/fixtures/routing-scenarios.ts)에 있다. 서울 역사마스터와 [관광공사 수원 위치](https://data.visitkorea.or.kr/linkedview/3075791), [인천 위치](https://data.visitkorea.or.kr/linkedview/947611), [수원 기관 안내](https://yeyak.syf.or.kr/www/119), [성남 좌표표](https://www.seongnam.go.kr/contents/down/10458_9.pdf)를 사용했다. 2026-10-05 확인 기록이며 성남 PDF는 검색 색인 표로 확인했고 직접 다운로드는 시간 초과했다. 공개 좌표는 검수된 만남 출입구가 아니며 중복 승강장·대표점 검토도 남아 있다.

2026-10-05에는 [방향 설명](https://help.traveltime.com/en/articles/9503877-how-do-departure-and-arrival-searches-differ)과 [경로 선택 설명](https://help.traveltime.com/en/articles/8523982-how-do-the-models-determine-which-route-to-take)을 참고해 정방향 출발 영역과 도착 경로를 구분했다. 당시 [Matrix 명세](https://docs.traveltime.com/api/reference/travel-time-distance-matrix)의 도착 시각 문구와 도움말 의미가 불일치해 공급자 확인 과제로 남겼다. 이는 과거 조사 기록이며 문서의 현재 표현을 새로 확인한 주장은 아니다.

[등시간권 명세](https://docs.traveltime.com/api/reference/isochrones)·[경로 예시](https://docs.traveltime.com/api/start/routes)는 문서상 기능의 근거다. 초기 대기·가장 늦은 출발·한국 시간표·도시 교통 범위의 정확성에는 별도 증거가 필요하다. [사용량 한도](https://docs.traveltime.com/api/overview/usage-limits)와 [오류 코드](https://docs.traveltime.com/api/reference/error-codes)는 참고 자료이며, 이번 422 원인의 직접 근거는 저장한 실제 오류 응답이다.
