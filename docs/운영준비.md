# 서버 운영 준비

현재 상태는 구현·로컬 검증 완료, 실제 공급자·운영 배포 검증 대기다. 운영 공개 승인, 검수 카탈로그, 공급자 계약과 실제 경로 검증을 대신하지 않는다.

## 실행 전 설정

- Workers `DB`는 D1 `wheretomeet-search-events`에 바인딩한다. 개발·운영 DB ID를 분리한다. 저장소의 0으로 된 DB ID는 운영용이 아니다.
- 서버 Secret: `KAKAO_REST_API_KEY`, `TRAVELTIME_APP_ID`, `TRAVELTIME_API_KEY`. 클라이언트에는 제한된 공개 Kakao JavaScript 키만 제공한다.
- `ROUTING_APPROVED=true`는 실제 교통 모드·한국 데이터·단조성·도착시각 검증을 승인한 후에만 설정한다. 기본 미설정은 503이다.
- `TRAVELTIME_HITS_PER_MINUTE`, `TRAVELTIME_HITS_PER_SEARCH`, `MAX_CONCURRENT_SEARCHES`는 양의 정수다. 분당 한도는 계약값 이하, 검색당 한도는 분당 한도 이하로 설정한다. 비공개 검증은 동시 검색 1개를 사용한다. 미설정·잘못된 값은 503이다. 예시 120/60/1은 설정 형식 설명이며 운영 허용량의 근거가 아니다.
- 운영에는 `ENVIRONMENT=production`과 `RATE_LIMITER` 바인딩을 설정한다. 바인딩이 없으면 외부 호출 API는 503으로 차단한다. Wrangler 형식은 `ratelimits: [{name: 'RATE_LIMITER', namespace_id: '<계정 내 고유 양의 정수>', simple: {limit: 60, period: 60}}]`이다. 60회/분은 초기 남용 방어 설정이며 실제 트래픽에 맞춰 검토한다.
- `data/hubs.json`이 비어 있거나 미검수 거점이 있으면 503 `CATALOG_NOT_READY`다. preview 카탈로그로 자동 전환하지 않는다.

Cloudflare rate-limit binding은 위치별·최종 일관성 방식이다. 정확한 전역 공급자 한도는 별도 D1 원자적 예약이 담당한다. [공식 rate-limit 문서](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)

## 전역 사용량과 취소

검색 전 단일 `INSERT ... SELECT ... RETURNING` SQL에서 활성 검색 수, 같은 익명 소유자의 중복 검색, 남은 hit 예산을 함께 확인하고 예약한다. D1 쓰기 직렬화가 Worker 인스턴스 간 중복 지출을 막는다. 모든 요청은 검색당 최대 hit 예산 전부를 90초간 예약한다. 검색은 30초 이내에 끝나므로, 마지막 공급자 호출 이후 60초의 rolling window까지 보수적으로 보호한다. 완료 시 동시성 lease만 해제하고 사용하지 않은 hit를 환불하지 않는다. 이 선택은 처리량을 낮추지만 취소·재시도·네트워크 불확실성에서 초과 지출을 피한다. lease는 35초 후 자동 무효화된다. D1 실패는 새 교통 호출을 차단한다.

입력 JSON 읽기, 행정구역 확인, 추천 계산에 하나의 30초 타이머와 취소 신호를 적용한다. 공급자 호출·재시도도 이 신호를 따른다. Kakao Retry-After는 남은 시간에 맞는 경우 한 번만 기다린다. 이미 시작한 호출은 취소해도 비용이 들 수 있다.

## 기록·통계·개인정보

`__Host-wtm` 쿠키는 32바이트 난수, Secure, HttpOnly, SameSite=Strict, Path=/다. DB에는 SHA-256 해시만 저장한다. HTTPS 운영이 필수다. 쿠키 삭제나 만료 후 기록에 다시 접근할 수 없고 기기 간 동기화는 없다. 익명 쿠키는 1년, 일반 기록은 마지막 성공/no_routes 검색 후 90일이다. 북마크가 있는 기록은 삭제 전까지 보관하고, 만료된 기록의 마지막 북마크 해제는 기록을 삭제한다. 추천을 다시 실행해도 기존 북마크는 보존된다. 서로 다른 검색에서 추가한 북마크 개수는 추천 최대 4개와 별개다.

`history`에는 복원에 필요한 출발지, 약속시각과 북마크만 저장하고 경로 응답은 저장하지 않는다. 읽기·수정·삭제는 소유자 해시와 기록 ID를 함께 검사한다. 변경 요청은 정확히 같은 Origin을 요구한다. 모든 `/api/` 응답은 no-store다.

`search_events`는 별도 통계다. 요청 ID, 계산 시작 UTC, 인원, 상태, 고정 오류 코드, 실제 반환 공개 거점 ID 최대 4개, TravelTime hits, 처리시간, 알고리즘/데이터 버전만 저장한다. 입력·사전 속도 제한 거절은 제외한다. 정상/빈 결과/오류/취소를 기록한다. 같은 요청 ID는 중복 저장하지 않는다. `waitUntil` 통계 실패는 원래 응답을 바꾸지 않는다. 성공 결과의 history 저장 실패는 응답의 `historySaved=false`와 `warning`으로 알린다.

로그에는 고정 실패 코드와 요청 ID만 남긴다. 원문 오류, 입력, 경로, 토큰, 주소, 좌표, 키, 원문 IP를 로그에 넣지 않는다. limiter에는 날짜와 IP의 해시만 전달하며 DB에 저장하지 않는다. 이는 익명성 보장이 아닌 단기 남용 방어 키다. 통합 Workers 설정은 사용자 코드의 고정 진단 로그를 켜고 `invocation_logs: false`로 자동 요청 로그를 끈다. Logpush/외부 프록시에서도 쿼리·요청 본문·Cookie 수집을 끄거나 마스킹해야 한다. 공개 장소 검색 `q`도 접근 로그에 남을 수 있다.

## 마이그레이션·정리·복구

Node24 환경에서 먼저 로컬 실행한다.

```powershell
npm run db:migrate
node --test tests/server-db.test.ts tests/server-api.test.ts
npm run typecheck
npm run build
```

운영 DB ID와 계정·환경을 검토하고 운영 적용 승인을 받은 뒤 명시적인 해당 환경 설정으로 `wrangler d1 migrations apply wheretomeet-search-events --remote --env production`을 실행한다. production 환경은 운영자가 별도로 구성해야 한다. 이미 적용한 마이그레이션은 수정하지 않는다. 배포 전에 D1 export/Time Travel 사용 가능 여부와 복구 절차를 개발 DB에서 검증한다. 코드 롤백을 위해 운영 DB를 삭제하지 않는다.

일일 cron `0 18 * * *`는 한국시간 03:00이다. 통계와 일반 기록에서 현재 UTC -90일보다 오래된 행을 삭제하고, 정확히 경계 시각인 행은 유지한다. 만료된 quota 예약도 삭제한다. `SEARCH_EVENT_CLEANUP_FAILED`, `HISTORY_CLEANUP_FAILED`, `QUOTA_CLEANUP_FAILED`, `QUOTA_RELEASE_FAILED`, `SEARCH_EVENT_WRITE_FAILED`, `HISTORY_WRITE_FAILED`를 감시한다. 저장과 정리는 best effort이며 통계를 과금 정산이나 quota 계산에 쓰지 않는다.

취소 시 이미 진행 중인 D1 쓰기는 중단할 수 없으므로, `waitUntil`로 완료를 추적한 뒤 소유자와 쓰기 revision이 일치하는 변경만 되돌린다. 이후 성공한 검색이나 기존 기록의 북마크 변경은 되돌리지 않는다. cleanup이 끝날 때까지 동시 검색 lease 해제를 지연한다. DB 장애로 이 보정까지 실패하면 `HISTORY_ROLLBACK_FAILED`를 별도로 기록한다. 이 경우 또는 Worker의 강제 종료에서는 DB 복구 후 운영 점검이 필요하며, 보정 완료를 성공으로 간주하지 않는다. 사용 중인 익명 쿠키는 토큰을 바꾸지 않고 1년 만료를 갱신한다.

기간을 한정한 운영 조회 예시:

```sql
SELECT date(searched_at,'+9 hours') AS korea_day, count(*) AS searches
FROM search_events WHERE searched_at >= '2026-10-01T00:00:00.000Z'
GROUP BY korea_day ORDER BY korea_day;

SELECT status,count(*) AS searches FROM search_events
WHERE searched_at >= '2026-10-01T00:00:00.000Z' GROUP BY status;

SELECT j.value AS hub_id,count(*) AS recommendations
FROM search_events,json_each(recommended_hub_ids_json) AS j
WHERE searched_at >= '2026-10-01T00:00:00.000Z'
GROUP BY j.value ORDER BY recommendations DESC;
```

Cloudflare 대시보드 및 D1 응답 메타데이터에서 DB 용량·rows_read·rows_written을 확인한다. SQL 요청 한 건이 쓰기 한 행이라는 가정은 하지 않는다. [D1 SQL API](https://developers.cloudflare.com/d1/worker-api/d1-database/), [Kakao Local API](https://developers.kakao.com/docs/ko/local/dev-guide)

## 아직 필요한 외부 증거

실제 Kakao/TravelTime 키·계약, 전역 운영 예산 설정, 검수 카탈로그, 실제 20×100 및 전체 규모 경로 비교, 지도/API 도메인, 실제 HTTPS 쿠키·Cloudflare 운영 D1·cron 실행·복구 검증이 필요하다. 로컬 SQLite/Worker 단위 검증은 이 항목을 PASS로 바꾸지 않는다.
