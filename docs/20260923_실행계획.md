# WhereToMeet 실행 계획

> 작성·공식 문서 확인: 2026-09-23. 제품 코드가 없는 신규 프로젝트를 기준으로 한다.
> 2026-10-05 갱신: Workers + D1에서 ORM 없이 직접 SQL로 검색 요약을 저장한다. 이번 공식 문서 재확인 범위는 D1·Workers 로그·백그라운드 작업이다.
> 구현 작업자는 `superpowers:executing-plans`를 사용해 아래 체크리스트를 순서대로 진행한다. 이 문서의 작성은 제품 구현·유료 계약·공개 배포의 실행을 의미하지 않는다.

**Goal:** 수도권에서 만나는 2~4명이 약속 시각까지 부담하는 시간을 비교해, 가장 부담이 큰 사람의 시간을 최소화하는 모임 거점과 주변 장소를 추천한다.

**Architecture:** React 모바일 웹을 PWA로 만들고 TWA로 Android 앱을 제공한다. Cloudflare Workers가 교통 API를 호출하고 등시간권·이분 탐색으로 후보를 찾은 뒤 도착시각 기준 경로로 검증한다. 거점 카탈로그는 정적 JSON으로 제공하고, 서비스 이용 통계용 검색 요약은 D1에 저장한다. 상세 오류 진단은 Workers Logs를 사용한다.

**Tech Stack:** TypeScript, React, Vite, PWA, TWA/Bubblewrap, Cloudflare Workers + D1, D1 기본 SQL API와 Wrangler SQL 마이그레이션, Kakao Maps JavaScript/REST API, TravelTime 일반 API, Turf의 점 포함 판정 모듈, Node.js 기본 테스트 러너. 초기 ORM은 사용하지 않는다.

**Spec:** [초기 서비스 구상](./20260922_아이디어구상.md)과 이 문서의 1~7절. 대화에서 확정한 선택이 원문의 미결정 사항보다 우선한다.

### Global Constraints

- 화면과 시각 표시는 한국어·한국 표준시(`Asia/Seoul`). API에는 시간대가 있는 ISO 8601을 전달한다.
- 입력 출발지와 추천 거점은 서울·경기·인천 안에 있어야 한다. 경로 미지원 지역은 명시적으로 안내한다.
- 외부로 보내는 좌표는 WGS84. `lat/lng`와 지도·GeoJSON의 `[lng, lat]`를 명시적으로 변환한다.
- 자동차, 택시, 항공, 시외·고속버스, 일반·고속열차를 추천 경로에 섞지 않는다. 수도권 전철·도시철도와 도시 내 버스를 검증 대상으로 삼는다.
- 등시간권은 후보 선별 수단이다. 폴리곤에 포함된다는 이유만으로 경로·도착 가능성을 확정하지 않는다.
- 실시간 운행 상태나 실제 도착 보장을 표방하지 않는다. 화면에는 계산 기준시각과 **예상** 시간을 표시한다.
- API 비밀키는 서버에만 둔다. 주소·참가자별 좌표를 공유 URL, 운영 로그, D1 검색 요약에 남기지 않는다.
- 무료 검증 단계는 개발자 통제 환경에서 수행한다. 상용 이용 권한·처리량·예산 확인 후 공개 운영한다.

## 2. 초기 구현 범위

### 2.1 무료 기술 검증판과 사용자용 MVP

**기술 검증판:** 공개된 장소를 출발지로 하는 고정 시나리오와 100개 거점으로 알고리즘을 검증한다. 이후 1,000~3,000개 거점 규모를 시험한다. 화면을 모두 만들기 전에 한국 교통 데이터·도착시각 계산·API 처리량이 성립하는지 판단한다.

**사용자용 MVP:** 검증을 통과한 거점 목록을 사용해 Android와 모바일 웹을 함께 제공한다. 1,000~3,000개는 원안의 카탈로그 목표이며, 이름만 다른 동일 역·플랫폼을 중복 집계해 개수를 채우지 않는다. 목표 규모를 확보하지 못하면 실제 규모와 누락 지역을 제시하고 출시 범위를 다시 결정한다.

### 2.2 사용자 흐름과 완료 조건

| 단계 | 초기 기능 | 완료 조건 |

공유는 원문의 **선택 후보지 공유** 범위로 한정한다. 다른 사람의 출발지나 전체 추천 결과를 복제하는 공유방은 만들지 않는다. 주변 가게까지의 마지막 이동은 거점 순위와 별도이며, 가게 선택 시 외부 지도에서 해당 가게를 목적지로 길찾기한다.

카카오 장소 검색은 기본 장소 정보와 상세 페이지 링크를 제공한다. 평점·리뷰·메뉴·영업 중 여부를 제공된 것으로 가정하지 않는다. ‘놀거리’는 우선 문화시설·관광명소로 구체화한다. 반경은 도보거리가 아니라 직선거리다. ([장소 검색 명세](https://developers.kakao.com/docs/en/local/dev-guide))

### 2.3 초기 범위에서 제외

회원가입, 공동 입력방·투표·채팅, 사용자별 검색 이력 조회·복원, 검색 입력·경로 원문의 영구 저장, 개인화, 자동차 혼합 추천, 실시간 파업·사고 반영, 예약·결제, AI Agent, 자체 대중교통 경로 엔진은 확장으로 둔다. 서비스 이용 통계용 검색 요약 저장은 초기 범위에 포함한다(6.3절). 첫 버전에서는 자동 현재 위치 취득 없이 장소 검색으로 입력해 위치 권한 없이도 전체 흐름을 사용할 수 있게 한다.

## 3. 핵심 알고리즘 설계

### 3.1 ‘중간’의 정의

약속 시각을 `D`, 참가자 `i`가 거점 `c`에 제때 도착할 수 있는 경로의 출발시각을 `L_i(c,D)`라고 한다. 검증된 경로 중 가능한 늦은 출발을 사용한다.

```text
부담시간 B_i(c) = D - L_i(c,D)
경로상 이동·대기시간 = arrival_i - departure_i
조기 도착 대기시간 = D - arrival_i
부담시간 = 경로상 이동·대기시간 + 조기 도착 대기시간

정렬 키 = (max(B_i(c)), sum(B_i(c)), 안정적인 거점 ID)
```

예: 이동 40분 + 조기 도착 대기 20분인 사람의 부담은 60분이다. 이동 55분 + 대기 0분이면 부담은 55분이다. 계산·동률 판정은 초 단위, 화면만 분 단위로 올림한다. 환승 횟수나 상권 점수로 이 순서를 바꾸지 않는다.

순위는 등록 거점과 공급자 경로 모델에 대한 추천이다. 수도권의 모든 장소에 대한 전역 최적해나 실제 이동시간의 최적해를 보장한다는 표현은 사용하지 않는다.

### 3.2 도착시각 기준으로 원안을 적용하는 방법

출발지에서 `arrival_search` 등시간권을 만들면 **그 출발지로 들어오는 영역**이 된다. 우리가 필요한 것은 **그 출발지에서 후보지로 가는 경로**다. 그대로 뒤집어 사용하면 버스 방향·운행시각이 다른 잘못된 문제를 풀게 된다. ([검색 방향 정의](https://docs.traveltime.com/api/overview/key-concepts))

검증할 방법은 다음과 같다.

1. 부담시간 한도 `T`를 정한다.
2. 각 출발지에서 `departure_time = D - T`, `travel_time = T`로 순방향 등시간권을 요청한다.
3. 등록된 거점 중 모든 참가자의 등시간권에 들어가는 거점을 찾는다.
4. 교집합 거점이 있으면 `T`를 줄이고, 없으면 늘린다.
5. 최종 후보들에 대해 **도착시각 `D`를 지정한 경로**를 조회하여 출발·도착시각을 검증하고 다시 정렬한다.

**성립 조건:** 해당 API의 순방향 시간 한도가 시작 대기를 포함해 `D`까지 도달 가능한 영역을 의미해야 한다. 시간이 커질 때 기다렸다 출발할 수 있어 도달 가능 집합이 줄지 않아야 한다. 이는 설계상 필요한 조건이며, 공개 문서만으로 이 서비스의 모든 입력에서 성립한다고 확인한 것은 아니다. 작업 0에서 버스 배차·막차·환승 사례로 검증한다. 성립하지 않으면 이 방식을 제품 코드로 확정하지 않고 4절의 Matrix 대안을 다시 결정한다.

### 3.3 이분 탐색과 후보 판정

- 최초 상한은 30분, 미충족 시 60 → 120 → 240분으로 늘린다. 당일 약속은 `D - 검색 시작시각`을 넘겨 과거 출발을 허용하지 않는다.
- 출발지 간 길찾기 시간의 최댓값을 상한으로 사용하지 않는다. 출발지는 추천 거점과 다르고, 시간표·방향·미도달 때문에 유효한 상한이 보장되지 않는다.
- 공통 거점이 확인된 상한 `high`를 확보한 후 `high - low <= 180초`가 될 때까지 탐색한다. `high`에서 구한 후보 집합을 보존한다.
- API 최소 시간 단위보다 작은 요청은 보내지 않는다. 정확히 같은 출발지·목적지는 별도 0초 경로로 처리한다.
- 폴리곤끼리 교차 도형을 생성하지 않고 각 거점이 각 등시간권 안에 있는지 검사한다. `shell`, `holes`, 여러 분리 도형을 보존한다. 경계점은 후보에 포함하고 경로 검증에서 판정한다.
- `range`는 사용하지 않고 시간 조건을 고정한다. 도보 접근·이탈 한도는 각각 15분을 초기값으로 두고 모든 탐색·경로 조회에 동일하게 적용한다. 제한 때문에 제외되는 입력은 안내한다.
- 동일 출발지에 대한 등시간권 요청은 한 번만 수행해도 되지만, 점수 합산에서는 참가자 수를 그대로 유지한다.
- 3분은 **탐색 구간의 폭**이다. 폴리곤 근사·시간표 오차까지 합쳐 실제 오차가 3분 이하라는 뜻이 아니다.

TravelTime의 폴리곤은 근사 표현이며 구멍 제거 옵션도 정확도에 영향을 준다. 따라서 구멍 제거·임의 버퍼 확대를 사용하지 않고, 원래 좌표를 그대로 경로 재검증에 전달한다. ([등시간권 명세](https://docs.traveltime.com/api/reference/isochrones))

### 3.4 최종 경로 조회와 순위 확정

최종 후보 집합 `F`의 **모든 거점**을 검증한다. 지리적 중심이나 상권으로 먼저 일부만 잘라내지 않는다.

- 일반 `/v4/time-filter`의 `arrival_searches`를 사용한다. **거점 하나당 search 하나**, 그 안의 `departure_location_ids`에 2~4명의 출발지를 넣는다.
- `arrival_time = D`, `properties = ["travel_time", "route"]`로 요청한다. 10개 search 이하씩 묶고 계약상 처리량을 지킨다.
- 응답 배열 순서가 아닌 `search_id`와 location ID로 사람·거점을 연결한다.
- `route.departure_time`, `route.arrival_time`을 검증하고 `D - departure_time`으로 부담시간을 직접 계산한다. `travel_time`에 조기 도착 대기가 포함되는지도 검증 기록에 남긴다.
- 약속 이후 도착, 현재보다 과거 출발, 허용하지 않은 교통수단, 한 사람이라도 미도달·시간정보 누락인 후보는 추천하지 않는다. 과거 출발 검사는 최종 응답 직전의 시각을 다시 읽어 수행한다. 버스·지하철 허용 범위를 API 설정으로 제한할 수 없는 경우는 작업 0의 채택 실패 사유다.
- 유효한 거점을 3.1절의 키로 정렬하여 최대 3개 반환한다. API가 제공한 경로 내 출발시각을 넘어 더 늦게 출발할 수 있다고 추정하지 않는다.
- 후보가 전부 경로 검증에서 탈락하면 상한을 3분 늘려 한 번 재확인한다. 여전히 실패하면 ‘해당 조건의 경로를 확인하지 못했습니다’로 처리하고 품질 실패를 기록한다.
- 최종 후보 수·응답 크기가 처리 예산을 초과하면 일부만 검사하고 ‘최적’으로 반환하지 않는다. 해당 검색을 처리 한도 오류로 종료하고 후보 분포·API 방식 재검토 대상으로 남긴다.

여기서 Matrix는 **등시간권으로 좁힌 후보의 도착 경로 검증**에 사용한다. 전체 후보를 Matrix만으로 탐색하는 대안과는 범위가 다르다. 시간·경로 의미와 위치 개수 제한은 실제 응답으로 확인한다. ([Matrix 명세](https://docs.traveltime.com/api/reference/travel-time-distance-matrix), [경로 응답 예제](https://docs.traveltime.com/api/start/routes))

## 4. Matrix 대안과 비교

| 방식 | 처리 방법 | 장점 | 제한·비용 | 이번 계획 |
| --- | --- | --- | --- | --- |
| 등시간권 + 이분 탐색 + 최종 경로 검증 | 2~4개의 등시간권으로 후보를 좁히고 최종 집합만 도착 경로 조회 | 원안을 유지하며 경로 조회 대상 감소 가능 | 반복 호출 지연, 폴리곤 근사, 도착 기준 성립 조건 검증 필요 | 우선 구현·검증 |
| 전체 Arrival Matrix | 모든 등록 거점에 대해 도착 기준 경로를 구하고 한 번 정렬 | 이분 탐색·폴리곤 판정 없음. 같은 모델·거점 집합의 전수 비교 가능 | 도착 기준은 **거점 수만큼 search** 필요. 무료 처리량으로 실시간 서비스하기 어려울 수 있음 | 검증 기준 및 전환 대안 |
| 소수 거점 + 국내 개별 길찾기 | 사전에 정한 적은 거점만 조회 | 국내 경로 비교와 작은 시제품에 유리 | 더 좋은 거점을 놓침. 예정 도착시각 지원도 별도 확인 필요 | 자동 대체하지 않음 |

**출발시각 기준과의 차이:** 같은 출발시각이라면 참가자별 one-to-many Matrix로 수천 개 도착지를 묶기 쉽다. 이번에는 같은 **도착시각**이므로 일반 API의 many-to-one 검색을 거점마다 만들어야 한다. ‘4명 × 3,000곳도 4회 조회’라는 계산을 적용하지 않는다.

TravelTime 일반 Matrix는 요청당 최대 10개 search, search당 최대 2,000개 상대 위치를 안내한다. `Fast`는 더 큰 행렬을 지원하지만 한국은 현재 Fast 지원국 목록에 없으며 날짜·시각 지정에도 제약이 있다. 이 프로젝트는 일반 API만 채택 후보로 삼는다. ([Matrix 규격](https://docs.traveltime.com/api/overview/travel-time-distance-matrix), [지원국](https://docs.traveltime.com/api/overview/supported-countries))

다음 중 하나이면 측정 결과와 운영 견적을 바탕으로 Matrix 전환 여부를 다시 질문한다.

1. 등시간권의 도착 마감시각 의미나 단조성 검증에 실패한다.
2. 전수 Matrix 대비 최장 부담시간 차이가 아래 품질 기준을 넘는다.
3. 반복 등시간권 호출 때문에 목표 응답시간을 넘고, 전수 Matrix가 계약 처리량 안에서 더 빠르다.
4. 최종 후보가 너무 많아 원안의 호출량 감소 효과가 없다.

전수 Matrix도 실패하면 후보 수·지원 지역·교통 모드·시각 기능을 바꾸는 선택이 필요하다. 사용자 결정을 받기 전에는 출발시각 기준이나 지하철 전용으로 조용히 변경하지 않는다.

TravelTime 지원표는 한국 대중교통을 Full로 표시하지만 독립적인 driving/walking/cycling은 None으로 표시한다. 이 표만으로 임의 주소의 보행 접근 구간까지 사용할 수 있다고 단정하지 않는다. Basic 키는 검증용이며 운영용 라이선스는 견적·이용 권한을 확인한다. ([지원표](https://docs.traveltime.com/api/overview/supported-countries), [요금·라이선스](https://traveltime.com/pricing))

카카오 대중교통 API의 실제 계정 사용 가능 여부와 날짜 조건은 검증 단계에서 확인한다. ODsay Basic의 안내 한도는 30회/일이므로 대량 비교를 무료 기본값으로 잡지 않는다. ([카카오 길찾기](https://developers.kakao.com/docs/en/kakaomap/rest-api), [ODsay 명세](https://lab.odsay.com/guide/releaseReference), [ODsay 사용·구매 조건](https://lab.odsay.com/contact/contact))

### 5.2 지도·장소

- Kakao REST: 출발지 검색, 주소 좌표 변환, 수도권 행정구역 확인, 주변 장소 조회.
- 지도·장소 공급자 출처와 로고 표시를 유지한다. 지도 결과를 수집해 별도 장소 DB를 만들지 않는다.

### 5.3 거점 카탈로그

거점 목록은 배포에 포함하는 정적 JSON으로 시작한다. 사용자의 출발지와 별개인 서비스 데이터다.

1. 국가철도공단 전체 기관 역사 자료에서 수도권 역을 추출한다. 공식 페이지에는 `전체_도시철도역사정보_20260630` 자료가 게시되어 있다. 역명만으로 합치지 않고 운영기관·역 식별자와 실제 환승 연결을 확인한다. ([역사 자료](https://data.kric.go.kr/rips/M_01_01/detail.do?id=32))
2. TAGO·지자체 공개 정류소/노선 자료에서 주요 버스 환승 거점을 보완한다. 정류소 이름이 같거나 도로 양쪽에 있다는 이유만으로 같은 만남 지점으로 합치지 않는다. TAGO의 서울·경기·인천별 실제 제공 범위를 확인하고 누락은 해당 지자체 자료로 채운다. ([TAGO 데이터 안내](https://tago.go.kr/v5/use/openapi.jsp))
3. 철도역 전수를 기본으로, 버스 거점은 노선 연결 수와 철도역이 없는 지역의 분포를 기준으로 후보를 만들고 보행 접근 가능한 대표 지점을 검수한다. 자동 추출 결과와 최종 채택 목록을 분리한다.
4. 각 항목에 안정적인 ID, 이름, 대표 좌표, 행정구역, 종류, 원본 ID·출처, 기준일, 검수 상태를 남긴다. 미검수 좌표는 출시 카탈로그에서 제외한다.
5. 100개 검증 목록 → 수도권 전체 1,000~3,000개 규모 순서로 확장한다. 주기적 자동 수집 시스템은 만들지 않고 월 1회 원천 변경을 확인해 검증 후 재배포한다.

원천 좌표를 곧바로 신뢰하지 않는다. 철도 데이터 제공기관도 위·경도 뒤바뀜 등의 수정 요청에 답변한 이력이 있다. 범위 오류, 빈 좌표, 같은 좌표의 중복 항목, 역 건물 밖의 비정상 좌표를 검사한다. ([제공기관 품질 안내](https://data.kric.go.kr/rips/M_04_04/detail.do?id=80&page=3))

## 6. 기술 스택과 최소 구성

| 영역 | 선택 | 이유·범위 |
| --- | --- | --- |
| 웹 UI | React + TypeScript + Vite | 입력·결과·장소 화면을 한 코드로 유지 |
| 날짜 입력·공유 | HTML 날짜/시간 입력, Web Share API, Clipboard | 별도 달력·공유 SDK를 먼저 추가하지 않음 |
| 설치형 웹 | PWA manifest, 최소 Service Worker | 정적 화면과 오프라인 안내만 캐시. API 응답·지도 타일은 캐시하지 않음 |
| Android | TWA + Bubblewrap | 웹 화면을 Android 배포 패키지로 제공. 도메인과 앱 서명 연결 필요 |
| 서버 | Cloudflare Workers + 정적 자산 | 비밀키 보관, 입력 검증, 교통 계산, 외부 API 중계 |
| HTTP | 기본 `fetch`, `AbortController` | 공급자 SDK 없이 필요한 엔드포인트만 호출 |
| 공간 판정 | `@turf/boolean-point-in-polygon` | 구멍·경계를 직접 구현하지 않음. 전체 Turf 패키지는 불필요 |
| 참조·계산 데이터 | 정적 거점 JSON, 요청 동안의 메모리 | 카탈로그 배포와 추천 계산에 사용 |
| 검색 통계 DB | Cloudflare D1, Workers의 `DB` 바인딩 | SQLite 계열 SQL DB에 검색 요약 저장. 상세 오류는 Workers Logs로 분리 |
| DB 접근·변경 | `env.DB.prepare(...).bind(...).run()`, Wrangler SQL 마이그레이션 | 직접 SQL과 값 바인딩 사용. Prisma·Drizzle·별도 DB 드라이버 미도입 |
| 상태 관리 | React 기본 상태 | 전역 상태 프레임워크가 필요한 범위가 아님 |
| 개발·검증 | Node.js 24 LTS, npm, TypeScript, `node:test` | 순수 계산·응답 정규화 테스트에 추가 테스트 프레임워크 불필요 |

TWA는 사용자의 지원 브라우저를 통해 웹을 전체 화면으로 표시한다. 도메인 검증 실패 시 브라우저 UI가 나타날 수 있으므로 배포용 서명으로 검증해야 한다. 서비스가 네트워크와 교통 API에 의존하므로 오프라인 추천은 제공하지 않는다. ([TWA 개요](https://developer.chrome.com/docs/android/trusted-web-activity), [서명·도메인 연결](https://developer.chrome.com/docs/android/trusted-web-activity/android-for-web-devs))

Cloudflare 무료 실행 한도에서 수천 거점과 복잡한 폴리곤 판정이 가능한지는 작업 0에서 CPU·메모리를 측정한다. 초과하면 유료 Workers 견적 또는 단일 Node 서버 비용을 제시하고 선택한다. Node 서버로 바꾸는 경우 D1 연결 방식이나 DB 변경 비용도 함께 검토한다. 검증 전부터 무료 운영을 보장하지 않는다. ([Workers 한도](https://developers.cloudflare.com/workers/platform/limits/), [요금](https://developers.cloudflare.com/workers/platform/pricing/), [Node 지원 버전](https://nodejs.org/en/about/previous-releases), [Turf 점 판정](https://turfjs.org/docs/api/booleanPointInPolygon))

### 6.1 서버 API 계약

| 서비스 API | 입력 | 출력·검증 |
| --- | --- | --- |
| `GET /api/places/search?q=...` | 2~100자 검색어 | 장소 ID·이름·좌표·주소. 검색 디바운스와 결과 선택 필요 |
| `POST /api/recommendations` | 2~4개 `origins`, 시간대가 있는 `meetingAt` | 최대 3개 거점, 개인별 경로·부담시간, 계산시각, 데이터 버전 |
| `GET /api/places/nearby?hubId=...&category=...` | 서버 카탈로그의 거점 ID, 허용된 분류 | 반경 800m, 최대 15개 장소. 요청자가 임의 반경·페이지 수를 확장하지 못하게 함 |
| `GET /meet/:hubId` | 공개 거점 ID | 선택 거점·주변 장소 화면. 출발지·약속 시각·이전 계산 결과는 포함하지 않음 |

`origins`의 원소는 `{id, label, lat, lng}`다. 서버는 인원, ID 중복, 숫자·좌표 범위, 시간 범위, 수도권 여부를 검증한다. 응답의 각 추천은 `{hubId, participantRoutes, maxBurdenSeconds, sumBurdenSeconds}`를 포함한다. 각 개인 경로에는 `{originId, departureAt, arrivalAt, travelSeconds, earlyWaitSeconds, burdenSeconds, transfers}`를 둔다. 원본 공급자 응답 전체는 브라우저로 전달하지 않는다.

### 6.2 오류·개인정보·비용 방어

- 입력 오류 400, 해당 조건의 경로 없음은 200의 명시적인 빈 결과 상태, 처리량 초과 429, 공급자 오류 502/503/504로 구분한다. 빈 결과와 타임아웃을 같은 것으로 처리하지 않는다.
- 검색 전체 제한시간의 초기값은 30초. 외부 호출은 잔여 시간 안에서만 수행하고 429·일시적 5xx는 `Retry-After`와 잔여 예산이 허용할 때 한 번만 재시도한다.
- 요청 취소·중복 클릭을 처리한다. 이미 시작한 외부 호출이 취소되어도 사용량이 발생할 수 있으므로 호출 횟수에 포함한다.
- 비공개 검증판은 동시 검색 1개와 공급자 전체 hit 예산을 적용한다. 공개판은 플랫폼의 속도 제한 기능과 공급자 한도를 설정한다. 여러 서버 인스턴스의 메모리 카운터만으로 전역 한도를 보장한다고 가정하지 않는다.
- 원문 검색어·좌표·API 키·경로 응답을 로그에 남기지 않는다. 플랫폼 접근 로그의 검색 쿼리도 마스킹하거나 수집을 끈다. Workers Logs에는 요청 ID, 알고리즘/데이터 버전, 호출량, 지연, 성공/오류 코드만 기록한다. 2026-10-05 확인 기준 보관기간은 Free 3일, Paid 7일이며, 장기 검색 통계는 6.3절의 D1에 저장한다. ([Workers Logs 보관 정책](https://developers.cloudflare.com/workers/observability/logs/workers-logs/#pricing))
- 추천 응답에는 `Cache-Control: no-store`를 적용한다. 앱·브라우저·Service Worker의 캐시에 다른 사람의 출발지와 경로가 남지 않게 한다. 서버의 검색 요약 저장은 6.3절의 허용 필드만 사용하며 추천 응답 전체를 저장하지 않는다.
- JavaScript 지도 키는 공개 클라이언트용 키로 도메인을 제한한다. REST 키·TravelTime 키는 서버 환경변수로 보관한다. `.env`, `.dev.vars`, 서명 키는 저장소에서 제외한다.
- 공유 문구와 장소명은 텍스트로 렌더링하고 외부 링크의 프로토콜·공급자 도메인을 검증한다.
- 공급자 경로·장소 응답의 재사용·장기 저장은 공급자 조건을 확인한 뒤 별도 기능으로 도입한다. 개인정보 처리 안내에는 검색 요약의 수집 항목·목적·보관기간도 반영한다.

### 6.3 D1 검색 요약 저장

**목적:** 검색량, 결과 없음·오류 비율, 추천 거점 분포, API 사용량과 지연 추세를 분석한다. 사용자별 검색 복원이나 경로 캐시는 제공하지 않는다. D1은 Workers의 `DB` 바인딩으로만 접근하고 개발·운영 DB를 분리한다. 관리자는 Cloudflare 대시보드나 Wrangler에서 기간을 지정한 SQL로 조회한다. 공개 통계 API·관리자 화면은 초기 범위에 넣지 않는다.

**저장 단위:** 입력 검증과 서비스 속도 제한을 통과해 추천 계산을 시작한 `POST /api/recommendations` 요청당 요약 한 건이다. 장소 검색 키 입력, 입력 오류·사전 속도 제한 거절, 작업 0의 CLI 검증은 포함하지 않는다. 따라서 이 테이블의 검색 수는 전체 HTTP 요청 수와 다르다.

`search_events` 테이블은 아래 필드만 갖는다. 서버가 생성한 요청 ID를 기본 키로 두고 `searched_at`에 기간 조회·삭제용 인덱스 하나를 추가한다.

| 필드 | 저장 계약 |
| --- | --- |
| `request_id` | `TEXT PRIMARY KEY NOT NULL`. 서버가 요청별로 생성한 UUID. 사용자·기기 식별자로 재사용하지 않음 |
| `searched_at` | `TEXT NOT NULL`. 추천 계산 시작 시각을 UTC ISO 8601로 저장 |
| `participant_count` | `INTEGER NOT NULL`. 중복 출발지를 포함한 참가자 수, `CHECK`로 2~4 제한 |
| `status` | `TEXT NOT NULL`. `success`, `no_routes`, `error`, `cancelled`만 허용 |
| `error_code` | `TEXT`, 정상·빈 결과는 NULL. 그 외에는 서버가 정한 코드만 저장하고 오류 메시지 원문은 저장하지 않음 |
| `recommended_hub_ids_json` | `TEXT NOT NULL`. 실제 반환한 공개 거점 ID 배열을 JSON으로 저장, 최대 3개. 추천이 없으면 `[]` |
| `traveltime_hits`, `duration_ms` | `INTEGER NOT NULL`, 각각 0 이상. 시작한 외부 호출의 사용량과 추천 처리시간; 재시도 사용량 포함, D1 저장 대기는 처리시간에서 제외 |
| `algorithm_version`, `data_version` | `TEXT NOT NULL`. 사용한 알고리즘·거점 카탈로그 버전 |

**저장·실패 처리:** `server/search-events.ts`의 `recordSearchEvent(db: D1Database, event: SearchEvent): Promise<void>`가 위 필드만 받는다. SQL은 고정하고 모든 값은 `bind()`로 전달한다. `ON CONFLICT(request_id) DO NOTHING`으로 같은 요청의 중복 기록을 방지한다. `server/index.ts`가 추천 처리 종료 시 한 번 호출하고 `ctx.waitUntil()`에 등록한다. 저장 실패는 `request_id`와 고정 코드 `SEARCH_EVENT_WRITE_FAILED`만 Workers Logs에 남기며, 이미 계산한 추천 결과나 원래 오류 응답을 바꾸지 않는다. ([D1 SQL 실행](https://developers.cloudflare.com/d1/worker-api/prepared-statements/), [waitUntil](https://developers.cloudflare.com/workers/runtime-apis/context/#waituntil))

초기 검색 통계는 저장 실패·실행 중단 시 누락될 수 있는 최선 노력 수집이다. 사용량 정산이나 전역 호출량 제한의 기준으로 삼지 않는다. 구현에 `ponytail: 검색 통계 누락 가능, 무손실 수집이 필요해지면 Queue 도입` 주석을 남긴다. 베타에서는 저장 실패와 플랫폼 실행 중단도 점검해 수집 상태를 보고한다.

**저장 제외:** 원문 검색어, 참가자 이름·주소·출발 좌표, 약속 시각, 개인별 경로, 공급자 응답 원문, API 키, IP 주소·사용자·기기 식별자는 D1에 넣지 않는다. 요청 본문 전체를 JSON으로 저장하지 않는다.

**보관·조회:** 검색 요약 보관 초기값은 90일이다. Workers의 일일 예약 작업에서 `deleteExpiredSearchEvents(db: D1Database, cutoffIso: string): Promise<void>`를 호출해 `searched_at < cutoffIso`인 행을 삭제한다. `cutoffIso`는 실행 시각에서 90일을 뺀 UTC 시각이며, 경계 시각과 같은 행은 유지한다. 삭제 실패는 고정 코드 `SEARCH_EVENT_CLEANUP_FAILED`로 기록하고 다음 예약 실행에서 다시 처리한다. 통계의 날짜 구분은 `Asia/Seoul` 기준으로 계산한다.

**스키마 관리:** `migrations/0001_search_events.sql`로 테이블과 제약·인덱스를 만들고 Wrangler로 적용한다. 이미 적용한 파일은 고치지 않고 후속 SQL 파일을 추가한다. ORM·사용자 테이블·일별 집계 테이블은 현재 필요하지 않다. ([D1 마이그레이션](https://developers.cloudflare.com/d1/reference/migrations/))

## 7. 무료 검증과 운영비 산정

### 7.1 호출량을 세는 방법

`n`: 서로 다른 출발지 수, `I`: 등시간권 반복 횟수, `M`: 최종 후보 수, `K`: 전체 등록 거점 수.

```text
원안의 TravelTime 사용량 ≈ n × I + M hits
원안의 HTTP 요청 수 ≈ I + ceil(M / 10)
전체 Arrival Matrix 사용량 ≈ K hits
전체 Arrival Matrix HTTP 요청 수 ≈ ceil(K / 10)
```

재시도·실패 후 재확인·개발용 전수 비교는 별도로 더한다. 출발지가 중복되어도 반환되는 사람별 부담시간은 2~4명 모두 유지한다. 최종 경로를 동일 Matrix 응답에서 받는 것을 전제로 한 계산이다.

예시: `n=4, I=8, M=40`이면 약 72 hits, 12 HTTP 요청이다. `K=2,000` 전체 Arrival Matrix는 약 2,000 hits, 200 HTTP 요청이다. 이는 설계상 계산 예시이며 실측치가 아니다. 한 HTTP 요청에 여러 search를 묶어도 hit 수가 하나가 되지 않는다.

현재 TravelTime Basic은 120 hits/분을 안내한다. 위 72-hit 검색도 계속 반복하면 처리량을 넘는다. 전수 Matrix 2,000-hit 검증은 처리량으로 환산해 약 16.7분 분량이며, 실제 실행시간에는 응답 지연과 제한 적용 방식이 더해진다. 무료 키는 공개 서비스 수용량의 근거가 아니다. ([사용량 정의·한도](https://docs.traveltime.com/api/overview/usage-limits))

카카오는 현재 대중교통 경로 1,000회/일, 장소 검색 항목별 100,000회/일 등의 무료 한도를 안내한다. 무료 적용 앱 여부와 계정 한도를 확인하고 유료 자동 사용은 검증 전에 활성화하지 않는다. ([공식 쿼터](https://developers.kakao.com/docs/en/getting-started/quota))

D1 사용량은 교통 API hits와 별도로 계산한다. 정상 수집 시 하루 `S`건의 추천 계산은 약 `S`개의 검색 요약 행을 추가하지만, 실제 과금 대상 읽기·쓰기 행 수에는 인덱스 갱신·통계 조회·보관기간 삭제도 포함된다. `rows_read`, `rows_written`, 저장 용량을 측정하며, SQL 요청 한 번을 쓰기 한 행으로 간주하지 않는다. ([D1 과금 기준](https://developers.cloudflare.com/d1/platform/pricing/))

### 7.2 통과 기준 — 모두 측정 목표이며 현재 달성한 수치가 아님

| 검증 | 표본·방법 | 초기 통과 기준 |
| --- | --- | --- |
| 시간 의미·방향 | 단방향 버스, 긴 배차, 막차, 환승, 자정 포함 | 반환 경로 전부 `departure <= arrival <= D`; 부담시간은 `D - departure`와 일치 |
| 등시간권 단조성 | 고정 D에서 여러 T를 증가시키며 100개 거점 판정 | 확인된 위반이 있으면 원인 해결 전 채택하지 않음 |
| 후보·정렬 정확성 | 20개 시나리오 × 100개 거점의 전수 Arrival Matrix와 비교 | 기준 경로가 존재하는 사례의 95% 이상에서 최장 부담시간 차이 3분 이하. 원안의 누락·오류도 실패로 집계. 한 사람이라도 못 오는 결과 0건 |
| 실제 규모 | 1,000~3,000개 카탈로그, 2·3·4명, 서울·경기·인천 조합 | 후보 검수 통과, 호출량·응답 크기·CPU·M 분포 기록. 작은 목록의 성능을 전체 규모로 단정하지 않음 |
| 응답시간 | 후보 판정·모든 API 대기를 포함한 검색 전체 측정 | 공개 MVP 목표 p50 5초 이내, p95 10초 이내, 30초 제한. 무료 키의 대기와 운영 계약상 처리량을 분리해 보고 |
| 한국 경로 품질 | 전철·버스·혼합 경로 각 10건 이상 검수 | 주요 구간·방향·환승 누락이 발견되면 원인과 지원 범위를 해결 |
| 실제 이용 점검 | 동의한 테스터의 실제 이동 10건 이상, 개인 주소 대신 구간 식별자로 기록 | 실제 소요시간과 예측 소요시간의 오차·지연 원인 기록. 초기 목표 중앙 절대오차 5분, p90 10분 이하 |
| 장애·키 보호 | 429, 5xx, 응답 일부 누락, 키 만료, 지도 실패, 취소 | 거짓 결과 없이 구분된 안내. 클라이언트 번들·로그에서 비밀키 0건 |
| 검색 요약 저장 | 로컬 D1에 정상·빈 결과·오류·취소, 같은 요청 ID 재기록, 만료 경계, DB 장애 재현 | 정상 DB에서는 대상 요청별 1행, 금지 필드 0개, 90일 초과 행 삭제·경계 행 유지. DB 저장 실패 시 원래 API 응답 유지와 고정 오류 로그 확인 |

검증 시나리오는 강남–홍대, 인천–서울, 수원–서울, 경기 동서 이동, 철도역에서 먼 버스 출발지, 동일 출발지, 운행이 끊기는 시각을 포함한다. 현재·주말·7일 후 약속을 구분한다. API 전수 비교는 합성된 공개 장소로 수행하고, 공급자 라이선스가 허용하는 방식으로 결과 요약만 보존한다.

동일 공급자의 전수 Matrix는 **후보 탐색 손실**을 평가하는 기준이지 현실의 정답은 아니다. 미래 시각을 받지 않는 국내 REST API 결과와 예정 약속 결과를 직접 빼서 정확도라고 부르지 않는다. 같은 시각 조건을 맞출 수 있는 자료와 실제 이동 관측은 별도로 평가한다.

후보 탐색 손실은 `원안 1위의 최장 부담시간 - 전수 Matrix 1위의 최장 부담시간`으로 계산한다. 기준 경로가 있는데 원안이 결과를 내지 못하면 성공률의 분모에서 빼지 않는다. 실제 이동 관측 10건은 초기 점검용이며 충분한 통계적 보증으로 해석하지 않는다.

### 7.3 유료 견적 요청에 넣을 정보

- 한국 대중교통 일반 `/time-map`, 도착 기준 `/time-filter`, 경로 표시가 가능한 계약인지.
- 일 100회·1,000회 검색을 각각 가정한 `실측 평균 hits × 검색수`, 피크 분당 검색수와 피크 HPM.
- 데이터 출처 표시, 공개 웹/앱 사용, 경로 결과 저장·재사용·검증 결과 보존 권한.
- 월 환산 비용뿐 아니라 연간 계약·최소 약정·세금·처리량·장애 지원 조건.
- 지도·Workers·D1·운영 로그·도메인 비용을 합친 총 운영비. D1은 검색 요약 90일 보관과 조회·삭제·인덱스 비용을 포함하고, 무료 로그 보관기간과 구분한다. 목표 규모별 금액을 받은 후 예산을 결정한다.

TravelTime 운영 요금은 현재 고정 라이선스·처리량 기반으로 안내되므로 확인되지 않은 ‘호출당 단가’를 만들어 계산하지 않는다. ([공식 가격 정책](https://traveltime.com/pricing))

### 작업 0. 한국 대중교통·도착시각·등시간권 성립 검증

**산출물:** `scripts/validate-routing.ts`, `data/hubs.sample.json`, `docs/검증결과.md`.
**선행 준비:** TravelTime 검증 키. 지도·국내 경로 비교에는 Kakao 키. 제품 UI는 아직 필요하지 않다.

- [ ] 공개 장소로 출발지 조합과 100개 거점을 만든다. 각 실행 시점에서 미래가 되도록 평일·주말·자정 시나리오의 날짜를 정한다.
- [ ] 기본 `fetch`로 일반 Time Map과 Arrival Matrix를 각각 호출하고 한국 좌표의 실제 응답을 확인한다.
- [ ] 같은 약속 시각에 30·45·60분으로 만든 등시간권과 도착 경로의 출발·도착시각을 비교한다. 긴 배차 사례에서 `D-T` 이후 출발하고 `D` 이전 도착하는지 확인한다.
- [ ] ‘빠르게 이동하지만 일찍 도착하는 경로’와 ‘더 늦게 출발해 정시에 도착하는 경로’를 구분하는 사례로 공급자의 도착 검색이 총 부담시간 기준에 맞는지 확인한다.
- [ ] 버스·전철 허용 범위, 보행 연결, 한국 노선·환승, 미래 7일 시간표, 폴리곤 단조성을 확인한다. 문서상 지원과 실제 응답을 구분해 기록한다.
- [ ] 20개 시나리오에서 원안과 전수 Matrix를 실행한다. 공급자 hit 한도에 맞춰 순차 실행하고 검증용 대기는 사용자 검색 지연과 따로 기록한다.
- [ ] 7절의 정확도·처리량·응답시간을 표로 기록한다. 실제 규모 데이터 준비 뒤에는 큰 카탈로그에서도 재검증한다.
- [ ] 실패가 있으면 재현 입력, 원인, Matrix 전환 또는 범위 조정 선택지를 제시한다. 통과하면 필요한 운영 처리량과 견적 질문을 확정한다.

**API 요청 형태 예시:** `D = 2026-09-26 15:00 +09:00`, `T = 60분`인 경우. 날짜는 설명용이며 실행 때 검증 날짜로 바꾼다.

```json
{
  "departure_searches": [{
    "id": "origin-a-60min",
    "coords": {"lat": 37.4979, "lng": 127.0276},
    "transportation": {"type": "public_transport", "walking_time": 900},
    "departure_time": "2026-09-26T14:00:00+09:00",
    "travel_time": 3600
  }]
}
```

최종 후보 조회는 같은 출발지를 향한 역방향 검색이 아니라 아래와 같이 **후보 거점을 도착지**로 둔다.

```json
{
  "locations": [
    {"id": "origin-a", "coords": {"lat": 37.4979, "lng": 127.0276}},
    {"id": "origin-b", "coords": {"lat": 37.5563, "lng": 126.9236}},
    {"id": "hub-1", "coords": {"lat": 37.5045, "lng": 126.9391}}
  ],
  "arrival_searches": [{
    "id": "hub-1",
    "arrival_location_id": "hub-1",
    "departure_location_ids": ["origin-a", "origin-b"],
    "arrival_time": "2026-09-26T15:00:00+09:00",
    "travel_time": 14400,
    "transportation": {"type": "public_transport", "walking_time": 900},
    "properties": ["travel_time", "route"]
  }]
}
```

예제의 `public_transport` 허용 수단은 실제 응답으로 확인한다. 필요한 수단 제한을 구현할 수 없으면 이 예제를 그대로 제품에 채택하지 않는다.

**검증 명령 계약:** 스크립트는 `--mode isochrone`과 `--mode matrix`를 받아 동일 시나리오를 비교하고, 키·정확한 개인 위치를 출력하지 않는다.

```powershell
node --env-file=.env scripts/validate-routing.ts --mode isochrone --catalog data/hubs.sample.json
node --env-file=.env scripts/validate-routing.ts --mode matrix --catalog data/hubs.sample.json
```

**완료:** 통과/실패 표, 원본 시나리오의 재현 방법, 평균·최대 hits, 지연, 미지원 조건이 기록되어 주 알고리즘 채택 여부를 판단할 수 있다. 키 없이 작성한 목업 결과로 통과 처리하지 않는다.

- [ ] 같은 파일의 회귀 검증에 구멍 속 거점 제외, 경계점 포함 후 경로 확인, 한 사람 미도달, 자정, 과거 출발, 단조성 위반, 공급자 실패를 추가한다.

**핵심 함수 계약과 회귀 테스트 시작점:** 구현 시 이 코드를 `tests/recommend.test.ts`에 넣는다. API 호출 없이 계산 오류를 잡는 최소 단위다.

```typescript
// server/recommend.ts에서 제공할 계약:
// rankCandidates(candidates: CandidateRoutes[], originIds: string[],
//   meetingAt: string, now: string): Recommendation[]
// CandidateRoutes = {hubId: string, routes: ParticipantRouteInput[]}
// ParticipantRouteInput = {originId: string, departureAt: string,
//   arrivalAt: string, transfers: number}
// Recommendation은 6.1절의 필드를 반환한다.

import test from 'node:test';
import assert from 'node:assert/strict';
import { rankCandidates } from '../server/recommend.ts';

test('최장 부담 우선, 동률은 합계, 누락·늦은 도착은 제외', () => {
  const at = (time: string) => `2026-09-26T${time}:00+09:00`;
  const route = (originId: string, start: string, end = '14:55') => ({
    originId, departureAt: at(start), arrivalAt: at(end), transfers: 0,
  });
  const candidates = [
    {hubId: 'A', routes: [route('a', '14:00'), route('b', '14:40')]},
    {hubId: 'B', routes: [route('a', '14:10'), route('b', '14:15')]},
    {hubId: 'C', routes: [route('a', '14:10'), route('b', '14:25')]},
    {hubId: 'missing', routes: [route('a', '14:50')]},
    {hubId: 'late', routes: [route('a', '14:50', '15:01'), route('b', '14:50')]},
  ];
  const result = rankCandidates(candidates, ['a', 'b'], at('15:00'), at('12:00'));
  assert.deepEqual(result.map(x => x.hubId), ['C', 'B', 'A']);
  assert.equal(result[0].maxBurdenSeconds, 50 * 60);
  assert.equal(result[0].sumBurdenSeconds, 85 * 60);
  assert.equal(result[0].participantRoutes[0].earlyWaitSeconds, 5 * 60);
});
```

**확인 명령:** `node --test tests/recommend.test.ts`와 `npm run typecheck`.
**완료:** 테스트 통과와 함께, 같은 20개 시나리오의 전수 비교가 7절 기준을 통과한다. 단위 테스트만으로 API 의미 검증을 대체하지 않는다.

### 작업 3. 서버 API·호출량 제한·검색 요약 저장

**파일:** `server/index.ts`, `server/search-events.ts`, `migrations/0001_search_events.sql`, `tests/search-events.test.ts`, Workers 설정, `.env.example`, `docs/운영준비.md`.
**선행:** 작업 2.
**저장 계약:** 6.3절의 `SearchEvent`, `recordSearchEvent`, `deleteExpiredSearchEvents`를 사용한다. D1 바인딩 이름은 `DB`, 운영 DB 이름은 `wheretomeet-search-events`로 두고 개발·검증 DB와 분리한다. 저장·정리는 서버 내부 작업이며 6.1절에 공개 API를 추가하지 않는다.

- [ ] 6.1절의 API를 구현한다. 추천은 POST로 받고 브라우저가 공급자 이름·외부 URL·호출 개수를 임의로 지정하지 못하게 한다.
- [ ] 인원·좌표·수도권 행정구역·약속 시각을 서버에서 검증한 뒤 교통 API를 호출한다.
- [ ] 전체 제한시간, 공급자 hit 제한, 요청 취소, 중복 요청, 재시도 한도를 적용한다.
- [ ] 429·키 만료·5xx·부분 응답을 재현한다. 잘못된 입력은 교통 API를 호출하기 전에 거부한다.
- [ ] 검색 요약 필드 제한·동일 요청 ID 중복·90일 삭제 경계·D1 저장 실패 시 응답 보존을 확인하는 회귀 테스트를 작성하고 실패를 확인한다. 정상·빈 결과·오류·취소 모두 기록 대상이며 입력 검증·사전 속도 제한 거절은 D1에 남지 않아야 한다.
- [ ] 6.3절의 SQL 마이그레이션과 `DB` 바인딩을 추가한다. 인원·상태·음수 사용량 제약을 적용하고, 로컬 D1에서 먼저 생성·적용을 확인한다. 초기에는 ORM을 설치하지 않는다.
- [ ] `recordSearchEvent`를 구현하고 추천 처리 종료 지점에 연결한다. 고정 SQL과 값 바인딩을 사용하며, `ctx.waitUntil()`에 등록한 저장 실패를 처리해 원래 응답을 유지한다. 같은 요청 ID의 재기록은 한 행으로 남아야 한다.
- [ ] 일일 예약 핸들러에서 `deleteExpiredSearchEvents`를 실행한다. 만료 경계보다 오래된 행만 지우고 삭제 실패를 운영 로그에 남긴다.
- [ ] 운영 로그·D1·오류 응답에서 입력 주소·좌표·비밀키가 노출되지 않는지 확인한다. 저장 가능한 필드만 명시적으로 구성하고 요청 본문을 통째로 전달하지 않는다.
- [ ] 회귀 테스트와 로컬 D1 검증을 통과시킨다. 개발 DB에서 실제 저장·기간 조회·삭제를 확인하고, 일별 검색 수·상태별 비율·거점별 추천 수 SQL과 D1 사용량 확인 방법을 `docs/운영준비.md`에 기록한다. 날짜 집계는 한국 표준시로 확인한다.
- [ ] 공개 베타 전에 실제 공급자 처리량에 맞춰 서비스의 분당 검색 수를 제한한다. HTTP 요청 수가 아닌 hit 수로 계산한다.

**확인 명령:** `npx wrangler d1 migrations apply wheretomeet-search-events --local`, `node --test tests/search-events.test.ts`, `npm run typecheck`, `npm run build`. 운영 DB 적용은 개발 DB 검증 후 해당 환경을 명시한 `--remote` 명령으로 수행하며 실행 방법을 운영 문서에 기록한다.
**완료:** 유효한 2명·4명 검색은 결과 또는 의미 있는 경로 없음 상태를 반환하고, 잘못된 1명·5명 입력과 과거 시각은 400으로 반환한다. 공급자 장애가 정상 빈 결과로 변환되지 않는다. 검색 요약이 7.2절 기준을 통과하고, DB 장애 때문에 추천이 실패하거나 민감정보가 저장되지 않는다.

### 작업 4. 모바일 웹 전체 흐름

**파일:** `src/App.tsx`, `src/Map.tsx`, `src/styles.css`.
**선행:** 작업 3. 디자인은 입력 → 비교 결과 → 장소 상세 세 화면으로 제한한다.

- [ ] 2~4명의 장소 입력과 한국 시각 기준 약속 입력을 만든다. 날짜 입력의 기기 시간대를 한국 시각으로 잘못 해석하지 않게 한다.
- [ ] 결과 카드에서 개인별 총 부담시간과 예상 출발시각을 먼저 보여주고 이동·조기 대기를 펼쳐 확인하게 한다.
- [ ] 카테고리 선택 때만 주변 장소를 조회한다. 식당·카페·문화/관광을 별도 필터로 제공한다.
- [ ] 선택 거점 서비스 링크와 외부 지도 링크 공유를 구현한다. 복사 성공·실패, 공유 취소를 구분한다.
- [ ] 지도 실패 시에도 결과 목록·주소·외부 지도 링크를 사용할 수 있게 한다.
- [ ] Android Chrome·삼성 인터넷·iOS Safari에서 검색 → 비교 → 주변 장소 → 공유를 확인한다. 모바일 웹은 Android 사용자만을 전제하지 않는다.
- [ ] 키보드 조작, 입력 라벨, 오류 초점, 화면 확대, 색상에만 의존하지 않는 참가자 구분을 확인한다.

**완료:** 설치·가입·위치 권한 없이 전체 흐름이 작동하고, 360px 폭과 큰 글자에서도 주요 버튼·시간이 잘리지 않는다. `npm run build`와 타입 검사가 통과한다.

### 작업 5. PWA·Android TWA·공유 링크

**파일:** `public/manifest.webmanifest`, `public/sw.js`, `public/.well-known/assetlinks.json`, `android/`.
**선행:** 작업 4, 운영 도메인과 Android 패키지 ID 결정.

- [ ] 앱 이름·아이콘·시작 URL·PWA manifest와 오프라인 안내를 준비한다.
- [ ] 소유한 HTTPS 도메인에 웹과 API를 배포하고 직접 공유 URL을 열어도 화면이 정상적으로 나타나는지 확인한다.
- [ ] Bubblewrap으로 Android 프로젝트를 생성하고 AAB를 만든다. 기기에서 뒤로 가기·외부 지도 전환·공유 후 복귀를 검증한다.
- [ ] 배포용 앱 서명의 SHA-256을 `assetlinks.json`에 등록한다. 업로드 키와 Play App Signing 키를 혼동하지 않는다.
- [ ] 앱 설치·미설치, 지원 브라우저·검증 실패 상황에서 링크를 확인한다. 앱이 없으면 정상 웹으로 연결한다.
- [ ] 내부 테스트 배포에 사용할 서명과 키 백업 위치, 배포/웹 롤백 절차를 기록한다.

**실행 순서:** 웹 배포 → manifest URL로 `bubblewrap init` → `bubblewrap build` → 내부 테스트 → 배포 서명으로 Asset Links 확인. 설정한 프로젝트의 명령은 npm 스크립트로 기록한다. ([TWA 구축 절차](https://developer.chrome.com/docs/android/trusted-web-activity/quick-start))

**완료:** 설치한 Android 앱과 모바일 웹에서 같은 기능을 사용하고 동일한 거점 링크가 열린다. 공개 Play 출시는 아래 계정 요건·심사를 별도로 충족해야 한다.

### 작업 6. 베타 검증·운영 전환

**파일:** `docs/검증결과.md`, `docs/운영준비.md`, 개인정보 안내 페이지.
**선행:** 작업 0~5, 공급자 운영 이용권 확인.

- [ ] 실제 사용자에게 지표를 설명하고, 지인 모임 등 10건 이상의 실제 이동으로 예측과 관측을 비교한다.
- [ ] 약속 성사에 필요한 장소를 찾았는지, 추천 결과에서 외부 지도를 열거나 공유했는지 테스트 참가자의 피드백으로 확인한다. 초기에 별도 행동 추적 SDK는 붙이지 않는다.
- [ ] 7절의 품질·성능 결과와 비용 견적을 함께 보고 공개 운영 여부·요금제를 결정한다.
- [ ] 연락 이메일, 개인정보 처리 안내, 공급자 표시, 스토어 스크린샷·설명·데이터 보안 정보를 준비한다.
- [ ] 제한시간·할당량 초과·교통 API 장애가 발생하면 신규 검색을 차단하고 상태를 안내하는 운영 절차를 확인한다.
- [ ] 배포 버전과 직전 안정 버전을 기록하고 웹·서버·거점 데이터 롤백을 점검한다.
- [ ] D1 저장 실패·용량·읽기/쓰기 사용량, 일일 만료 삭제를 점검한다. 검색 요약 90일 보관을 개인정보 안내에 반영하고, 개발 DB에서 백업·복구와 이전 코드의 스키마 호환성을 검증한다. 코드 롤백을 위해 운영 DB를 삭제하지 않는다.
- [ ] 공개 배포 직전에 사용자의 출시 의사와 최종 운영비를 확인한다.

**완료:** API 사용권, 검증 기준, 비용, 두 플랫폼 동작, 출시 자료를 모두 충족한다. 대기 중인 공급자 계약이나 스토어 심사를 구현 완료와 혼동하지 않는다.

### 8.2 순서·예상 공수

`작업 0 → 1 → 2 → 3 → 4 → 5 → 6` 순서다. 공급자 문의와 테스트 계정 준비는 개발과 병행할 수 있다.

| 작업 | 개발자 1명 기준 계획용 범위 |
| --- | --- |
| 0. API·알고리즘 검증 | 3~5 작업일 |
| 1. 거점·기반 구성 | 2~4 작업일, 데이터 검수량에 따라 증가 |
| 2. 추천 계산 | 3~4 작업일 |
| 3. 서버 API·D1 검색 요약 | 3~5 작업일 |
| 4. 웹 전체 흐름 | 3~5 작업일 |
| 5. Android 패키징 | 2~3 작업일 |
| 6. 통합 검증·출시 준비 | 2~4 작업일 |

총 18~30 작업일의 초안이다. D1 저장·정리·장애 검증을 작업 3에 포함했다. 담당자의 숙련도·API 검증 실패에 따라 변하며 견적 회신, 실제 이동 관측, Play 비공개 테스트·심사 대기시간은 별도다. 확정 출시일은 작업 0 결과와 계정 상태를 확인한 뒤 정한다.

### 9.3 선택했을 때만 필요한 준비물

- **ODsay 비교를 추가할 때:** ODsay 키와 대량 검증·운영 사용 조건 확인. 주 알고리즘 검증의 필수 키는 아니다.
- **공공 API로 거점 자료를 수집할 때:** 해당 TAGO/지자체 서비스의 활용 신청·서비스 키. 공개 파일 다운로드로 충족되면 API 키는 필요 없다.
- **실시간 버스·지하철 기능을 추가할 때:** 도시별 실시간 도착 API와 정류소 ID 매칭 자료.
- **AI 기능을 선택할 때:** 모델 API 계정·비용 예산. 초기 버전에는 필요 없다.

API 가입·요금 결제·도메인 구매·타인에게 테스터 요청을 보내는 일은 이 계획 작성 중 실행하지 않았다.

| 8 | 타 지역·지역 간 이동 | 수도권 데이터·운영비 검증 후 | 지역별 거점과 지원 범위, 시외·철도 시간표 및 환승 모델 |
| 9 | iOS 앱 | 모바일 웹으로 충족되지 않는 이용 수요 확인 | 배포 방식 재검토, Apple 계정·빌드 환경. TWA를 그대로 iOS 앱으로 전환하지 않음 |
| 10 | AI 보조 | 자연어 약속 조건 입력이나 추천 설명에서 명확한 효용 확인 | 입력 구조화·검증. 이동시간·운행 경로·순위의 근거는 교통 API와 계산 로직 유지 |

## 11. 다음 실행과 후속 결정 시점

**가장 먼저 할 일은 사용자용 화면 제작이 아니라 작업 0의 API 검증이다.** TravelTime 개발 키로 도착 기준 등시간권의 의미와 한국 경로 품질을 먼저 확인한다. Kakao 키가 준비되면 지도·장소·국내 경로 비교도 함께 검증한다.

| 결정 시점 | 사용자에게 제시할 자료 | 필요한 결정 |
| --- | --- | --- |
| 작업 0 검증 실패 | 재현 사례, 원안/Matrix 정확도·호출량·지연 비교 | Matrix 전환 또는 기능/지역 범위 조정 |
| 무료 처리량·실행 한도 초과 | 필요한 HPM, 서버 자원, D1 읽기·쓰기·저장량, 실제 비용 견적 | 운영비 상한과 공급자·호스팅 선택 |
| 거점 전체 수집 완료 | 검수된 개수와 지역별 누락 | 목표 규모·지원 지역 조정이 필요한 경우 결정 |
| Android 패키징 전 | 사용 가능한 도메인·패키지 ID·서비스명 후보 | 장기 유지할 운영 식별자 선택 |
| 공개 출시 전 | 검증 결과, 견적, 앱·웹 동작, 배포 자료 | 운영 계약과 공개 출시 여부 |

현재 계획에서 사용자 선택을 기다리는 기능 항목은 없다. 외부 API의 실제 성립 여부와 유료 운영비는 **작업 0의 산출물을 보고 결정하도록 정해진 실행 단계**다. 최신 공식 문서 확인은 수행했으며, API 실호출·성능 측정·앱 구현은 아직 수행하지 않았다.
